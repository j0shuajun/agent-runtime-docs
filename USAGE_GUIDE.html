Usage Guide

이 문서는 Agent Runtime를 호출할 때 요청마다 어떤 값을 준비해야 하는지 정리한 가이드입니다. 빠르게 호출해 보고 싶다면 Quickstart를 먼저 보시고, endpoint별 상세 규격은 Endpoints를 함께 참고해 주세요.

먼저 이해할 것​

Agent Runtime의 chat 요청은 OpenAI-compatible payload에 orch metadata를 추가해서 보냅니다. messages는 모델이 읽는 대화 내용이고, orch는 Agent Runtime가 세션, 권한, 검색 범위, 중복 요청 여부를 판단하기 위해 사용하는 metadata입니다.

팁

먼저 GET /v1/models, GET /v1/indices를 호출해 운영 환경에서 허용된 값을 확인한 뒤, 그 값을 chat 요청에 전달하는 방식을 권장합니다.

Request body
{
  "model": "<model-id-from-catalog>",
  "stream": true,
  "messages": [
    {"role": "user", "content": "배포 지연의 원인과 권장 조치를 설명해줘"}
  ],
  "orch": {
    "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
    "x_request_id": "896cd7ad-8e3c-4c85-b918-a294d133c44e",
    "identity": {"user_id": "user-1"},
    "rag_params": {
      "index": "rag-index",
      "permission_groups": ["example-team"]
    }
  }
}

messages​

messages는 사용자가 보는 대화 이력입니다. 최소 하나의 message가 필요하고 system은 한 개까지 입력 규격상 허용되지만 agent graph context에서는 제외됩니다. Caller가 service-owned system prompt를 바꾸는 용도로 사용할 수 없습니다.

같은 chat_id로 user-visible transcript 전체를 다시 보내는 client도 지원합니다. 서버는 checkpoint와 일치하는 prefix를 제외하고 새 suffix만 graph에 추가합니다. 다만 과거 message 내용을 수정하면 prefix matching이 깨져 이력이 다시 추가될 수 있으므로, 이전 대화는 임의로 바꾸지 않는 것이 안전합니다.

max_tokens, max_completion_tokens, temperature, top_p, frequency_penalty, seed, stop, generation_config은 client 호환을 위해 받지만 validation 전에 폐기되어 Main Agent나 Internal LLM 설정을 바꾸지 않습니다. Caller가 선택하는 응답 transport 설정은 stream입니다.

값 준비 기준​

값값의 출처규칙비고
model/v1/models의 data[].id서버 catalog에서 받은 값을 그대로 사용합니다.model 선택 UI나 호출 설정에서 관리합니다.
user_id로그인 사용자 또는 업무 시스템의 사용자 식별자실제 내부 사용자 식별자를 전달합니다.Knox AD ID처럼 안정적인 값을 권장합니다.
permission_groupsauth/권한 시스템이 계산한 그룹 목록임의로 넓히지 않고 실제 사용자 권한을 전달합니다.RAG, MCP, Skill, Agent 노출 범위가 함께 달라집니다.
index/v1/indices의 값하나의 문자열로 전달합니다.Chat은 comma-separated string을 허용하고, 빈 문자열이면 설정된 전체 RAG index를 사용합니다. Search Proxy의 빈 index_name은 422입니다.
chat_id사용자 서비스에서 생성한 UUID4새 대화마다 만들고 같은 대화에서는 유지합니다.multi-turn, HITL resume, thread workspace의 기준입니다.
x_request_id사용자 서비스에서 생성한 UUID4새 사용자 요청마다 새로 만듭니다.같은 요청을 네트워크 재시도할 때만 재사용할 수 있습니다.

user_id​

user_id는 Agent Runtime가 사용자 세션, usage log, tool 실행 context, 사용자별 장기 Memory와 과거 대화 소유권을 구분하는 기준입니다.

위험

user_id, chat_id, x_request_id에는 실제 요청자를 구분할 수 있는 값을 보내야 합니다. orch를 생략하거나 user_id가 비어 있거나 literal "user_id"인 경우, 또는 chat_id/ x_request_id가 nil UUID이면 400 invalid_identity로 거절됩니다. UUID 형식 자체가 잘못되었으면 request schema 검증에서 422 validation_error가 발생합니다.

permission_groups​

permission_groups는 단순 표시용 값이 아닙니다. 이 값에 따라 RAG 문서 접근, MCP server, Skill, Agent의 노출 범위가 함께 달라집니다.

경고

permission_groups는 임의로 넓혀서 보내면 안 됩니다. auth 시스템에서 계산한 실제 사용자 권한을 그대로 전달해야 합니다.

영향 범위설명
RAG retrievalRAG API가 접근 가능한 문서만 검색하도록 필터링합니다.
MCP visibility요청 권한 그룹에 허용된 MCP server만 runtime에 노출됩니다.
Skill visibility허용된 Skill만 main agent와 subagent가 볼 수 있습니다.
Agent visibility허용된 Agent만 subagent 후보가 됩니다.
Manifest 해석Router가 capability를 볼 때 실제 운영 권한 정책과 맞춰 해석해야 합니다.

예시:

Request fragment
{
  "permission_groups": ["example-team", "restricted-team"]
}

index​

index는 Agent Runtime가 검색할 corpus를 정하는 값입니다. 먼저 catalog를 조회해 실제 운영 환경에서 허용된 index를 확인합니다.

정보

index는 UI label이 아니라 RAG backend가 이해하는 실제 index name입니다. 화면에는 사람이 읽기 쉬운 이름을 보여주더라도 API payload에는 /v1/indices에서 받은 값을 그대로 사용합니다.

Request
curl "$AGENT_RUNTIME_API_BASE/v1/indices"
Response
[
  "rag-index"
]

index는 하나의 문자열입니다. Chat에서는 단일 index만 검색할 수도 있고, 여러 index를 comma-separated 형식으로 연결할 수도 있습니다. 빈 문자열은 현재 RAG_INDEX에 설정된 전체 public RAG index를 사용하라는 의미입니다.

Request fragment
{
  "rag_params": {
    "index": "rag-index",
    "permission_groups": ["example-team"]
  }
}
Multiple indices
{
  "rag_params": {
    "index": "rag-index,example-index",
    "permission_groups": ["example-team"]
  }
}
All indices
{
  "rag_params": {
    "index": "",
    "permission_groups": ["example-team"]
  }
}

주의할 점:

입력Chat orch.rag_params.indexSearch Proxy index_name
허용된 단일 값해당 index를 사용합니다.해당 index를 사용합니다.
comma-separated 값allowlist에 있는 항목만 검색 범위로 해석합니다.모든 항목이 allowlist에 있어야 하며, 하나라도 없으면 422입니다.
빈 문자열설정된 전체 RAG index를 사용합니다.422 index_name must not be empty로 거절됩니다.
wildcard 포함 값allowlist에서 제외됩니다.422로 거절됩니다.

Chat은 허용되지 않은 항목을 조용히 검색 범위에서 제외하므로, caller는 요청 전 /v1/indices로 값을 검증해야 합니다. 잘못된 index를 오류 응답으로 감지하려면 Search Proxy처럼 다루지 말고 client 쪽에서 catalog allowlist를 강제해 주세요.

chat_id​

chat_id는 대화 thread id입니다. LangGraph checkpointer, hitl_pending, HITL resume, same-session single-flight guard와 내부 /workspace가 이 값을 기준으로 동작합니다.

팁

사용자가 대화 목록에서 이전 대화를 다시 열 수 있는 UI라면, 각 conversation record에 chat_id를 함께 저장해 주세요. 후속 질문과 HITL 답변은 이 값을 재사용해야 같은 대화로 이어집니다.

권장 생성 방식:

Python
import uuid

chat_id = str(uuid.uuid4())

사용 기준:

사용자 동작chat_id
새 대화 시작새 UUID 생성
같은 대화에서 후속 질문기존 UUID 유지
HITL 질문에 답변기존 UUID 유지
이전 대화 다시 열기저장해 둔 기존 UUID 사용

Agent가 내부 작업 파일을 만들었다면 같은 user_id:chat_id를 재사용할 때만 이어집니다. 다른 chat_id를 만들면 이전 대화의 /workspace 파일도 보이지 않습니다. 이 파일은 사용자에게 직접 다운로드되는 artifact가 아니며, 최종 결과는 기존과 같이 assistant message로 받습니다.

같은 user_id:chat_id에서 이미 stream이 진행 중이면 다음 요청은 409 session conflict로 거절될 수 있습니다. 화면에서는 한 대화 안에서 이전 stream이 끝난 뒤 다음 질문을 보내도록 처리해 주세요.

HITL 질문과 답변은 여러 HTTP 요청이지만 운영 조회에서는 하나의 interaction으로 연결됩니다. 클라이언트는 여전히 같은 chat_id와 새 x_request_id만 지키면 됩니다. 서버가 각 요청의 run_id, 최초 요청을 가리키는 interaction_id, 직전 요청을 가리키는 parent_run_id, 0부터 증가하는 phase_index를 관리합니다.

x_request_id​

x_request_id는 호출자가 request body에 넣는 한 API 요청의 idempotency/correlation id입니다. 서버는 이 값을 받은 직후 내부 context와 PostgreSQL에서는 request_id라는 이름으로 정규화합니다.

경고

새 사용자 질문마다 x_request_id를 새로 만들지 않으면 409 duplicate_request가 발생할 수 있습니다. 같은 네트워크 요청을 재시도할 때는 중복 workload를 막기 위해 같은 x_request_id를 쓸 수 있지만, 서버가 이전 응답을 재생하지는 않고 재시도 요청을 409 duplicate_request로 닫습니다.

권장 생성 방식:

Python
import uuid

x_request_id = str(uuid.uuid4())

사용 기준:

상황x_request_id
사용자가 새 질문을 보냅니다.새 UUID 생성
같은 질문을 네트워크 문제로 재시도중복 실행 방지가 필요하면 같은 UUID를 쓰고 409 duplicate_request를 처리
사용자가 stop 후 다시 질문새 UUID 생성
HITL 답변 제출새 UUID 생성
화면 새로고침으로 같은 request가 다시 전송될 수 있는 구조중복 submit이 아닌지 UI에서 먼저 막는 것을 권장합니다.

같은 dedup scope에서 같은 x_request_id가 이미 처리된 경우 409 duplicate_request가 발생합니다. 이 오류는 서버가 같은 요청을 두 번 실행하지 않았다는 의미입니다.
