FAQ

orch.rag가 비어 있으면 RAG 검색이 안 된 건가요?​

아닙니다. Chat terminal의 orch.rag.source_urls, contexts, doc_images는 호환성을 위해 빈 구조로 유지합니다. 실제 retrieval/tool 실행 근거는 /v1/runs에서 run_id를 찾은 뒤 GET /v1/runs/{run_id}/evidence로 확인하세요. 최종 답변의 인용 링크는 assistant message 본문에서 확인합니다.

같은 x_request_id로 재시도하면 이전 응답을 받을 수 있나요?​

아닙니다. 같은 user_id:chat_id 범위에서 이미 사용한 x_request_id를 다시 보내면 서버는 workload를 두 번 실행하지 않고 409 duplicate_request로 닫습니다. 이전 응답 body를 재생하는 idempotent response cache는 아닙니다.

Chat의 빈 index는 되는데 Search Proxy의 빈 index_name은 왜 422인가요?​

두 endpoint의 계약이 다릅니다. Chat의 빈 orch.rag_params.index는 현재 설정된 모든 public RAG index를 사용합니다. Search Proxy는 검증된 명시적 검색 경계이므로 빈 index_name, wildcard, allowlist 밖의 값을 422로 거절합니다.

/health가 200인데 Chat은 왜 실패하나요?​

/, /health, /metrics는 process가 HTTP 요청을 받는지만 확인하는 shallow check입니다. PostgreSQL, RAG, LLM gateway, MCP를 요청마다 probe하지 않습니다. Chat 실패시 public error code, pod log의 correlation field, dependency 상태를 별도로 확인하세요.

새 chat_id에서도 이전 정보를 기억하나요?​

같은 user_id의 장기 Memory는 새 chat_id에서도 사용될 수 있습니다. Memory는 반복적인 사용자 사실·선호를 user scope로 다루며 /memories/MEMORY.md에 read-only로 보입니다. 반면 선택한 대화의 실제 message, HITL, /workspace는 user_id:chat_id thread scope입니다. 다른 사용자의 Memory나 대화는 조회할 수 없습니다.

system, temperature, max_tokens로 Agent 정책을 바꿀 수 있나요?​

아닙니다. Request system message는 한 개까지 schema 검증을 통과하지만 agent graph context에서 제외됩니다. temperature, top_p, max_tokens, max_completion_tokens, frequency_penalty, seed, stop, generation_config도 호환성을 위해 받지만 validation 전에 폐기됩니다. Service-owned prompt와 generation 정책을 caller가 바꾸지 못하며, caller가 선택하는 transport 설정은 stream입니다.

Agent가 쓰는 파일은 다른 사용자나 다른 대화에서도 보이나요?​

아닙니다. /workspace는 user_id:chat_id thread별 내부 작업 공간입니다. 같은 사용자의 같은 chat에서는 다음 요청이나 다른 API process에서도 PostgreSQL checkpoint를 통해 이어지지만, 새 chat_id나 다른 사용자는 그 파일을 볼 수 없습니다.

배포의 assets/skills, assets/agents는 별도 공용 원본입니다. 현재 요청에 허용된 항목만 Agent-visible /skills, /agents에 read-only로 보이며 workspace로 복사되지 않습니다.

Agent가 파일을 만들면 사용자가 다운로드할 수 있나요?​

아닙니다. 현재 /workspace는 Agent가 초안과 중간 분석을 정리하는 내부 공간입니다. Download endpoint나 artifact card를 제공하지 않으므로, Agent는 파일을 만들었더라도 실제 요청 결과를 최종 채팅 본문에 포함해야 합니다. 화면에는 filesystem 작업이 [Tool] write_file 같은 기존 tool progress 형식으로 보일 수 있습니다.

Agent가 shell이나 Pod의 실제 파일을 읽을 수 있나요?​

아닙니다. Agent filesystem은 Pod의 실제 /가 아니라 /workspace, /memories, /skills, /agents만 있는 default-deny virtual filesystem입니다. /memories/MEMORY.md는 현재 사용자의 read-only 장기 Memory입니다. Shell/execute, assets/mcp_server.json, route되지 않은 host 파일은 노출하지 않습니다. /skills, /agents, /memories 쓰기도 backend와 permission에서 거부합니다.

Chat에 사용된 RAG 결과는 어떻게 보나요?​

Chat 실행 후에는 Runs API의 evidence 조회로 확인합니다. 먼저 /v1/runs에서 사용자의 실행 목록을 조회해 run_id를 찾고, GET /v1/runs/{run_id}/evidence를 호출하면 chat 중 실행된 observation과 각 input/output을 볼 수 있습니다.

RAG 결과만 보려면 observations[]에서 type="tool"이고 검색 tool 이름인 항목을 찾습니다. 실제 질의는 input, 검색 결과는 output에 있습니다. 실행 결과는 임의 preview로 자르지 않은 sanitized JSON-safe 형태로 보존됩니다.

어느 agent가 tool이나 Skill을 실행했는지 어떻게 알 수 있나요?​

Evidence의 중첩 구조를 그대로 읽으면 됩니다. Main/subagent Agent의 observations 배열 안에는 그 agent가 실행한 model, tool, Skill과 nested subagent가 실제 순서대로 들어갑니다.

Subagent가 실행한 검색 tool
{
  "type": "agent",
  "name": "researcher",
  "observations": [
    {
      "type": "tool",
      "name": "rag_search",
      "input": {"query": "배포 지연 원인", "index": "rag-index"},
      "output": {"results": [{"title": "Deployment Delay Overview", "score": 0.82}]}
    }
  ]
}

위 tool은 researcher Agent의 observations 안에 있으므로 해당 subagent가 실행한 것입니다. Skill과 model 호출도 같은 방식으로 소유 agent 아래에 놓입니다. 별도 ID를 맞춰 public tree를 다시 조립할 필요가 없습니다.

MCP, tool, RAG 권한 관리는 어떻게 되나요?​

요청의 orch.rag_params.permission_groups를 기준으로 통제합니다.

대상통제 방식
RAG retrievalpermission_groups가 RAG backend로 전달되어 사용자가 접근 가능한 문서만 검색합니다.
MCP server/toolaccess.permission_groups가 선언된 server만 요청 group과 교집이 있을 때 runtime에 노출됩니다. 선언이 없거나 빈 목록이면 public입니다.
Skillaccess.permission_groups가 선언된 Skill만 교집이 필요합니다. 선언이 없거나 비어 있으면 public입니다.
Agentaccess.permission_groups가 선언된 Agent만 교집이 필요합니다. 선언이 없거나 비어 있으면 public입니다.

permission_groups가 뭔가요?​

permission_groups는 삼성전자 DS 내부 인증/권한 체계에서 계산된 SSG group 기반 리스트입니다. 사용자 서비스는 로그인한 사용자의 실제 권한 group 목록을 받아 orch.rag_params.permission_groups에 그대로 전달해야 합니다.

이 값은 임의로 넓혀 보내면 안 됩니다. 비어 있거나 실제 권한과 다르면 RAG 검색 결과가 줄거나, 제한된 MCP, Skill, Agent가 runtime에 보이지 않을 수 있습니다.

permission_groups는 어디에 쓰이나요?​

permission_groups는 한 요청 안에서 두 가지 역할을 합니다.

  1. 어떤 자료를 검색할 수 있는지 정합니다.
  2. 어떤 MCP, Skill, Agent가 모델에게 보일지 정합니다.

요청 예시는 다음과 같습니다.

{
  "orch": {
    "rag_params": {
      "permission_groups": ["MASK_DEV", "ORG_PROCESS"],
      "index": "rag-index"
    }
  }
}

MASK_DEV와 ORG_PROCESS는 request body 형식을 보여 주기 위한 예시입니다. ORG_PROCESS가 모든 요청에 필요한 고정 그룹이라는 뜻이 아니며, 실제 로그인 사용자의 권한 시스템에서 받은 그룹 목록을 전달해야 합니다.

index 값은 무엇을 뜻하나요?​

index는 RAG 검색을 시작할 후보 corpus 범위입니다.

Agent Runtime UI를 사용하는 경우에는 사용자가 화면에서 선택한 index 값이 요청에 들어갑니다. API를 직접 호출하는 경우에는 caller가 orch.rag_params.index 또는 Search API의 index_name에 직접 넣은 값이 사용됩니다.

중요한 점은, 요청에 index가 들어갔다고 해서 그 index 안의 모든 chunk가 답변 생성에 활용된다는 뜻은 아니라는 것입니다. RAG API는 선택된 index 범위를 RAG API에 전달하지만, 최종 검색 가능 여부는 RAG Portal에 업로드된 각 chunk의 permission_groups와 요청의 permission_groups가 교차하는지로 다시 필터링됩니다.

예를 들어 요청 index가 rag-a,rag-b이고 사용자의 권한 group이 example-team뿐이라면, RAG backend는 두 index 안에서도 chunk별 permission group에 example-team과 교집합이 있는 chunk만 검색 후보로 사용합니다. 따라서 DB나 요청 payload에 index가 보이더라도, 권한 교집합이 없는 index/chunk는 최종 근거나 답변 생성에 쓰이지 않습니다.

RAG 검색에서는 어떻게 적용되나요?​

RAG 검색 tool이 실행되면 요청의 permission_groups가 RAG API로 전달됩니다.

예를 들어 사용자가 example-team 권한만 가지고 있으면, RAG backend는 그 사용자가 볼 수 있는 문서만 검색 결과로 돌려줍니다. RAG API가 검색 결과를 받은 뒤 임의로 권한을 넓히거나 추가 문서를 붙이지 않습니다.

MCP, Skill, Agent는 어떻게 보이거나 숨겨지나요?​

MCP, Skill, Agent는 각각 access.permission_groups를 가질 수 있습니다.

  • access.permission_groups가 없으면 기본적으로 보입니다.
  • 값이 있으면 요청의 permission_groups와 하나라도 겹칠 때만 보입니다.
  • 겹치지 않으면 모델은 그 MCP, Skill, Agent가 있는지도 모릅니다.

예를 들어 선택적 MCP가 restricted-team 권한을 요구하고, 요청 권한이 ["example-team"]뿐이면 그 MCP는 tool 후보에 들어가지 않습니다.

큰 입력이 거절된 뒤 같은 대화를 계속할 수 있나요?​

네. Streaming 응답에 loop.stop_reason=context_input_too_large와 “입력 내용이 처리 한도를 초과하여 요청을 실행하지 못했습니다”가 보이면 그 큰 입력은 active conversation state에 넣지 않습니다. 같은 chat_id와 새 x_request_id로 짧은 질문을 다시 보내면 정상 처리합니다.

다만 거절된 원문은 모델이 보존하거나 복원할 수 없습니다. “아까 긴 내용을 요약해 줘”처럼 그 내용을 참조하면 내용을 나누어 다시 제공하라고 안내합니다. FE가 전체 transcript를 다시 보내도 runtime은 content-free cursor로 거절된 큰 입력과 fallback을 건너뜁니다. Langfuse의 raw inbound trace는 기존 관측 계약상 남을 수 있으므로, 여기서 “저장되지 않았다”는 말은 active conversation context에 포함되지 않았다는 뜻입니다.

호출 오류가 나면 무엇부터 확인하나요?​

증상보통 원인확인할 것
400 invalid_identityorch가 없거나 user_id가 비어 있거나 "user_id"이거나, chat_id/x_request_id가 nil UUID입니다.실제 user_id, UUID 형식의 non-nil chat_id, x_request_id를 전달합니다. 형식 오류는 422입니다.
알 수 없는 modelcatalog에 없는 model id를 보냈습니다./v1/models에서 받은 id만 사용합니다.
409 duplicate_request같은 user_id:chat_id에서 x_request_id를 재사용했습니다.새 사용자 요청마다 새 UUID를 만듭니다. 재시도에 같은 UUID를 쓰면 이전 응답 재생 없이 409로 중복 실행만 막습니다.
409 session conflict같은 대화에서 이전 stream이 끝나기 전에 다음 요청을 보냈습니다.같은 user_id:chat_id의 이전 stream 종료를 기다립니다.
검색 결과가 너무 적음permission_groups가 비어 있거나 실제 권한과 다릅니다.DS 내부 권한 mapping과 전달 payload를 확인합니다.
기대한 corpus가 검색되지 않음index가 다른 corpus를 가리킵니다./v1/indices에서 허용 index를 확인합니다.
HITL 후 대화가 이어지지 않음HITL 답변에서 새 chat_id를 만들었습니다.같은 chat_id, 새 x_request_id로 재개합니다.
HITL 질문·답변이 Langfuse에서 하나의 trace로 합쳐져 보임이전 interaction-based trace 데이터이거나 trace seed가 run_id로 전환되지 않았습니다.새 HITL interaction으로 재현해 각 run_id별 LangGraph trace와 PG의 phase 관계를 함께 확인합니다. 기존 trace는 소급 분할되지 않습니다.
잘못된 run cursor이전 조회 조건과 다른 조건에서 next_cursor를 재사용했습니다.같은 query 조건에서 받은 cursor만 재사용합니다.
upstream timeout/unavailableRAG/provider 의존성이 응답하지 않습니다.dependency 상태와 timeout 설정을 확인합니다.
409 run_not_terminalRuns list에는 보이지만 아직 terminal outcome이 없습니다.완료·HITL·실패 중 하나로 종료된 뒤 detail/evidence를 조회합니다.
observability unavailableterminal summary는 있지만 Langfuse artifact를 읽지 못했습니다.chat 장애와 구분해 Langfuse URL·key·worker·반영 지연을 확인합니다.
context_input_too_large새 user 입력 하나가 compaction token trigger보다 큽니다.내용을 여러 요청으로 나눈 뒤 같은 chat_id, 새 x_request_id로 다시 보냅니다.
