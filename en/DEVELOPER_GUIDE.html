Developer Guide

This guide covers runtime configuration, streaming, observability, PostgreSQL, MCP, and assets for developers/operators. See Usage guide for caller request rules.

Runtime env​

Startup validates required and conditional settings. Changes require restart. New booleans accept trimmed, case-insensitive true/false only; unset uses the default, while blank/other values are errors. Feature OFF differs from a configured dependency failure.

warning

Any configured Langfuse/Rerank value requires its complete group. Internal connectivity uses required INTERNAL_LLM_MODEL to select a catalog entry, including with personalization OFF because compaction still needs the selected model and credential reference.

Turn Evaluation replaces the former Continuation Gate retry budget. complete permits Memory/summary postprocessing; needs_revision returns to the compiled Main model within the revision budget. Initial and revised answers stream immediately. Processing progress appears only before an actual revision and is hidden with details OFF. One Main invocation's chunks concatenate unchanged; distinct valid blocks receive the needed blank line consistently in SSE, terminal, non-stream, and storage. Internal evaluation instructions never enter the user answer.

Evaluation uses a fixed 30-second overall budget for its one model request, JSON/schema validation, and automatic Memory planning, independently of LLM_TIMEOUT. Timeout, Internal LLM failure, or critical schema failure preserves the latest Main answer and skips revision/persistence. Memory and conversation-summary decisions validate independently: one invalid side effect does not discard a valid completion/revision decision.

Each LLM evaluation attempt makes one physical call. The default request omits max_completion_tokens; it does not impose a fixed 4K output ceiling. All Internal LLM use cases inherit endpoint extra_body options and recursively overlay use-case controls and the final reasoning_effort="none", chat_template_kwargs.enable_thinking=false, stream=false policy. Other nested options survive; Main/Subagent use endpoint options without this Internal override. An explicit use-case output limit takes precedence over both endpoint token-limit aliases. Serving limits and the existing deadline still apply. Unsupported controls follow the serving implementation; no model-specific option removal or retry is performed.

Response-envelope validation precedes termination/content checks. Explicit finish_reason=length always fails before content parsing, even for apparently valid JSON. Existing failure_reason distinguishes the following outcomes:

ReasonMeaning
output_truncatedThe provider ended generation with length.
empty_contentNo usable text, without an explicit length termination.
invalid_jsonContent exists but JSON parsing fails.
invalid_schemaJSON parses but the existing evaluation contract fails validation.

Malformed envelopes retain invalid_response; timeout and transport reasons retain their existing meanings. An absent finish reason follows the existing content path. Failed results are not applied or sent for another JSON-repair model call. Normal needs_revision still returns to Main, and existing Memory planning can make its own call. The four-field output schema and independent Memory/summary normalization remain unchanged.

Evaluator reads direct current-turn dialogue and RunItem call/result IDs/native status. Tool arguments and bodies are omitted with or without compaction. Compaction result, archive preservation, prior gap, and runtime notice remain available. Summary is historical context, not direct user evidence for new Memory facts.

Compaction policy​

Compaction timing and recent retention use the executing Main/Subagent model's catalog capacity and Native policy. max_input_tokens means the deployed server's max model len: the total context shared by input and generated output. The native 85% trigger, 10% keep window, and safe Tool/HITL boundaries remain. One service replacement occupies the existing middleware slot. Both Agents generate summaries through the catalog connection selected by INTERNAL_LLM_MODEL.

HITL resume answers already consumed by a matching ask_user Tool result are used only to match replayed Frontend history. They are not appended again as Human messages. A valid completed transcript cursor takes precedence over an earlier user-only prefix; combined Frontend Assistant narration/progress/final text is not copied back into the checkpoint. A later genuine request with the same wording remains a separate occurrence.

The first compaction summarizes all messages leaving recent context. Later compactions use the previous successful summary plus all newly evicted messages. There is no 4K tail selection. Internal compaction budgets come from the selected Internal model's total catalog capacity C. They are ceilings, with integer division and 1K = 1024 tokens:

Internal capacitySource chunkMerge inputOutput ceiling
64K16K32K8K
128K32K64K16K
256K64K128K32K
512K128K256K64K
1M / 2M128K256K64K

The formulas are min(128K,C//4), min(256K,C//2), and min(64K,C//8). The assembled prompt, instructions, and output reservation must also fit C. These policies are code-owned and take precedence over endpoint output limits; no compaction-specific budget configuration is added. A serving system's separate generation limit is not inferred from total context capacity.

Source chunks prefer whole user turns and matching Tool call/result groups. Only oversized groups split into messages, and only oversized messages split at paragraphs/lines or lossless ranges. Parts retain source order, role, call ID, and part number in the summary prompt; they are not independent executions. Every selected source range is included.

Completed summaries are packed as whole ordered documents under the separate merge budget. Only an oversized document splits internally at sections. Each stage uses at most ten active calls per request and collects results in source order. Failure or cancellation cancels and awaits all siblings. A stalled merge gets one bounded compact rewrite; continued nonprogress fails into the existing fallback. There is no semantic quality grader or arbitrary compression ratio. A single source chunk needs no merge.

Before applying the new summary, the Native boundary and the final service model-input boundary check summary + recent originals + System context + Tool definitions against the existing Native input budget, including configured output reservation and its existing headroom. Only the new summary may be compressed once more. If it still cannot fit, retain the previous-summary/gap fallback; if that also cannot fit, fail explicitly. This gate does not delete Keep or the current user request, and does not add a tokenizer or alter Provider overflow recovery.

Compaction instructions and the final continuation/archive/summary wrapper use Markdown headings and blank lines. Existing XML/prefix checkpoint summaries remain readable. Recompaction passes the prior summary body, archive facts, runtime notice, and existing metadata without nesting old continuation wrappers. Runtime control tags and raw source whitespace retain their meaning.

Instructions preserve goals, completed/pending work, important values/IDs/paths/Tool results, user corrections and cancellations, decisions, constraints, unresolved issues, and context gaps. Raw messages remain in checkpoints and evicted source is archived under /runtime/conversation_history/. Both archive storage and summarization must succeed before applying a new summary.

OutcomeNext model input
Both succeedNew summary + recent original messages
Either fails, prior successful summary existsPrior summary + accurate gap notice + recent originals
Either fails, no prior successful summaryGap notice + recent originals

A failed replacement summary is not applied, and nonexistent archive paths are not advertised. Fallback permits continuation without claiming lost facts were recovered. A gap survives later successful compaction, restart, and Subagent inheritance. Main and Evaluator receive the same compaction result, archive preservation, gap, and runtime notice through shared RunItem interpretation. This does not copy giant Tool arguments/results into evaluator input.

Repeated compaction
A + B + C → successful summary S1
S1 + D + E → archive fails → keep S1 + gap notice + recent F
Next successful compaction → summarize S1 and new source, retaining the prior gap

Recover needed details only from archives that actually exist: search with grep, then use read_file with offset/limit. Do not inject archives wholesale. Latest user corrections and cancellations take precedence; historical Tool/MCP text and Assistant prose are not new authority.

Native FilesystemMiddleware preserves oversized Tool originals under /runtime/large_tool_results/ and supplies model previews/recovery paths. Private /runtime is separate from user /workspace quota and rejects model writes/edits. Runs evidence returns recorded originals rather than substituting those previews.

Streaming announces logical compaction and uses its wording for heartbeats while any parallel scope remains active. It returns to ordinary heartbeat after the last scope ends. Fallback is announced once per compaction. Both locales work with details OFF and notices use line breaks.

Langfuse retains logical compaction and its physical summary Generations. Call counts depend on chunk/merge depth. Runs places only compaction occurrence and applied/fallback outcome at the owning Agent's timeline position; private summary instructions/bodies remain hidden. loop.compaction counts logical compactions, not physical chunk calls.

Main, Subagent, and Internal requests retain selected-model credentials and existing Bearer/X-dep-ticket/api-key, sender, user, and conversation headers. Each physical request gets a fresh Prompt-Msg-Id within the same Chat-Id. Existing bounded provider-overflow recovery remains; callers must split a current user input that is itself too large. Routed history appends only the suffix beyond the matching checkpoint prefix. Checkpoint read failure is not empty history.

System prompt and Harness Profile​

Service identity, search policy, and filesystem rules remain in configs/system_prompt.jinja2. Harness Profile is an official middleware extension point, not a second hardcoded prompt policy.

A caller's single system text stays request-local configurable data. Main middleware appends an authority wrapper and a JSON-string serialized instruction after the service runtime context. Serialization separates structure from caller text; it does not erase instruction meaning. Subagents do not include this middleware, and Evaluator/compactor use separate internal boundaries. Nothing persists into messages/checkpoints or silently carries into later requests/resumes.

Runtime resolves the Main/subagent model profile and replaces the Native summarization slot with the service compaction middleware using the same middleware name. Native Trigger, Keep, and Overflow recovery remain; the service owns archive application and Internal summary budgets. Concurrent graph compilation does not mutate a library-global factory.

Why can requests end around 300 seconds before LLM_TIMEOUT?​

Ingress, API gateway, or load-balancer read/idle timeout may expire first. The application setting cannot extend those policies. 300 seconds is not a fixed repository default; check annotations, controller ConfigMaps, and gateway policies.

Storage​

At startup and then daily, the server collects conversations whose latest trusted activity is six calendar months old. TIMEZONE determines calendar dates with month-end clamping; comparisons use UTC instants. Activity combines RunIndex and the latest Native checkpoint in each namespace. Updating conversation_summary alone does not extend retention.

Under the existing session lease, a transaction rechecks activity/state and deletes all namespaces from native checkpoints, checkpoint_blobs, checkpoint_writes plus the matching conversation_summary row. Runtime archives, large results, and state-backed workspace disappear with checkpoint state. Any intermediate failure rolls back the whole deletion.

Running RunIndex, accepted Usage, HITL/native interrupts, valid leases, and uncertain timestamps or ownership protect data. Existing cancellation can leave RunIndex running, which is protected too; six months is not an unconditional deletion deadline. Stale running records are not expired by an invented policy. User Memory, API Keys, permissions, Usage, RunIndex, Langfuse, and OpenWebUI records remain. Runs can still read recorded Langfuse evidence after raw checkpoint collection. Shutdown cancels the GC task before closing database resources. No new TTL variable or table is introduced.

Main-only update_user_memory accepts add/update intentions rather than a rewritten Markdown document; semantic targets, dates, and atomic editing are handled by the shared Memory planner. It requires personalization ON. delete_user_memory remains available ON/OFF: clear needs no Internal LLM, while partial requires its configured connection. Updates return updated/unchanged/conflict/failed; delete conflicts reread/replan until success. Automatic edit proposals use the same path, skip stale versions, exclude turn-local deletion targets, and may retain unrelated facts. No additional environment settings are needed.

DEFAULT_LOCALE selects fixed system text; legacy labels and unrelated dates remain readable. Formatting changes are saved only with real changes. Automatic planning shares the existing evaluation budget and cannot invalidate a delivered answer or independently valid summary. Management/history labels remain hidden; natural narration and trace evidence are preserved.

Memory management, past-conversation list/read, and read_file/grep confined to /memories/, /runtime/large_tool_results/, or /runtime/conversation_history/ hide labels even with details ON. General file and Skill labels keep their policy; events/traces remain. Optional narration and result prose are generated by the model.

Trusted sender names are not credentials

Trusted senders skip Key and Permission lookup and accept supplied groups. Ingress/API Hub must bind or validate these names for authenticated internal callers; ordinary external users must not choose them freely.

Key registration and lifecycle​

POST a base-name System binding without changing environment or redeploying. POST preserves other active Keys. PATCH changes only valid future expiry of an active Key; inactive returns 409 api_key_not_active. DELETE retains the row and first revocation timestamp. See API Key management.

What execution appears in evidence?​

Subagent args/actual return appear once on their Agent node with nested internal activity. Compaction appears at its timeline position with applied/fallback outcome, without summary bodies. Oversized observations remain whole on one page. Reads page all existing semantic markers and resolve ownership from Native namespaces. See Runs.

No separate tool-selection list exists in MCP configuration. Recorded Main/subagent, model, MCP/tool, Skill, guardrail, HITL, and errors appear as semantic evidence. Tool outputs are JSON-safe, and failed observations retain error.message rather than disappearing. Unrecorded provider-private reasoning cannot be reconstructed.

Evaluation is not a graph execution node. Validated responses/failure records stay in ordered run.artifact.output.turn_evaluation. Unconfigured evaluation leaves an empty array; failure records have completion_status="failed", persistence no-op values, and stable failure_reason, without raw exceptions, provider bodies, prompts, or Memory content.

Why do x_request_id and Prompt-Msg-Id differ?​

The former identifies one caller request; the latter separates each physical LLM call within it. Never copy the inbound request ID into outbound provider IDs. Chat-Id groups calls belonging to one conversation.

Does HTTP 200 mean streaming succeeded?​

No. Failure after response start has terminal finish_reason=error; HITL has hitl and awaits input. Inspect terminal reason, not just HTTP status or [DONE]. Non-stream Agent failure instead returns HTTP 500 error envelope.

Internal LLM​

INTERNAL_LLM_MODEL is always required and selects an ID from the active catalog. Main/Subagent use their actual model's catalog entry. Internal URL and credentials come from the selected entry; INTERNAL_LLM_BASE_URL and INTERNAL_LLM_X_DEP_TICKET are no longer read. Personalization OFF still requires Internal connectivity for compaction and completion evaluation.

Evaluation, Memory Planner, Deep Search S1, and compaction share catalog connections and always send both reasoning_effort=none and chat_template_kwargs.enable_thinking=false, with stream=false, regardless of model family or provider. The common HTTP client applies this policy to the first three use cases; compaction keeps its LangChain ChatOpenAI path and applies the same controls when configuring that model. Each use case still owns its prompt, schema, output budget, timeout, and failure policy.

All Internal paths first inherit the selected endpoint's extra_body. One common recursive merge applies endpoint options, then use-case controls, then the final Internal policy above. Objects merge recursively; other values, including arrays, are replaced. Other nested options survive. For example, Internal requests retain configured temperature=0.7 and custom_option="keep" while disabling reasoning/thinking. Explicit use-case output budgets replace both endpoint token-limit aliases, max_tokens and max_completion_tokens. Shared configuration is never mutated.

Unsupported controls are handled by the upstream serving implementation. Runtime does not detect capabilities, remove options, retry without them, or select a model-specific reasoning fallback. An upstream rejection follows the use case's existing failure policy. Models that reject reasoning_effort="none" still cannot use this Internal policy.

Evaluation, Memory Planner, and Deep Search do not specify an output token cap by default. Compaction retains its dynamic output budget: min(65536, capacity // 8), where capacity is the selected Internal model's deployed max_input_tokens. Its summarization, merge, parallelism, fallback, Native compaction, and checkpoint behavior are unchanged.

A nonempty normal final answer receives narrow semantic completion evaluation. A promise such as “I will check” needs revision; substantive answers, clarification questions, and explained failures are complete. Evaluation does not grade answer quality or required Tool use. Missing visible final text produces the same needs_revision history in code without an LLM call and reenters the existing Main loop. A complete response also supplies Memory proposals and conversation summary in the same evaluator response. Existing Memory-edit planning may require a separate call; evaluation history count therefore need not equal physical evaluator call count.

Evaluation failure preserves the latest answer and skips side effects. Each evaluation attempt makes one model call without a fixed 4K output cap or JSON-repair retry. The existing 30-second total budget includes validation and optional Memory planning. failure_reason distinguishes output_truncated, empty_content, invalid_json, and invalid_schema; timeout/transport reasons retain their existing meanings. Normal Main revision, partial persistence validation, and Memory processing remain unchanged.

Deep Search S1 makes a single Internal LLM planning attempt. Invalid JSON, schema or plan, empty content, output truncation, timeout, or request failure immediately uses the existing rule-based plan: original query, empty subqueries and keywords, and llm_used=false. Missing connection settings skip the attempt. Strict JSON Schema and existing plan validation, normalization, and count limits remain. Variant selection, parallel RAG search, deduplication, rerank, result shape, and existing diagnostics continue unchanged. For example, a malformed plan for “service latency causes” still searches that original query without a repair call.

Model catalog​

Catalog entries contain model ID, compatible URL, deployed capacity, credential reference, and optional extra_body request options. api_key uses the same ${ENV_NAME} expansion as MCP config. Models sharing a key reference the same variable; only models requiring a different key need another reference. Never put actual keys in JSON/Git. Missing or empty referenced values fail startup rather than selecting another key.

      "enable_thinking": true,

    }
  }
}

Values, including false, zero, and null, are preserved without option-name or value inference. Runtime-owned top-level keys are rejected in extra_body: model, messages, stream, stream_options, tools, tool_choice, response_format, base_url, api_key, and max_input_tokens. Credentials and capacity remain separate catalog fields. Public model listings do not expose these options.

max_input_tokens keeps its name but means the server's deployed max model len: total context shared by input and output, not a separate output setting. It maps to the same LangChain profile field. /v1/models retains its public response. An absent/empty MODEL_ENDPOINTS_CONFIG_PATH selects configs/endpoints.json. That override remains supported and documented, but is omitted from .env.sample.

Initial regional installation​

Choose TIMEZONE at first deployment and retain it during operation. Existing Korean services use an unset value or Asia/Seoul with their existing Usage defaults. Usage rows, KST Memory dates, checkpoints, Runs, and conversation summaries are not rewritten; no timezone migration CLI is needed. Other regions use independent new deployments/storage.

The DBA preserves shared standards.usage_log_base types/defaults and other services. Prepare the new child's complete columns, inheritance, constraints, and indexes, then align only that child's created_at default with its region. For an already prepared US West child:

New US West service child default
ALTER TABLE agent_runtime_us_west.agent_runtime_us_west
  ALTER COLUMN created_at SET DEFAULT
  (now() AT TIME ZONE 'America/Los_Angeles');

Deploy with SERVICE_NAME=agent_runtime_us_west and TIMEZONE=America/Los_Angeles. Startup rejects mismatched child defaults without automatically altering tables. Keep existing Korean child defaults as now() AT TIME ZONE 'Asia/Seoul'.

Connections apply the service search path and TIMEZONE. Older connections did not override session timezone; confirm their actual DBA environment with SHOW TimeZone. Aware inputs, timestamptz, and explicit regional conversions preserve instants despite session display changes. API dates use the request application's TIMEZONE and retain explicit offsets' instants.

Naive Usage timestamps store local wall clocks and cannot distinguish the two instants in a repeated DST hour. Use existing timestamptz execution records for precise chronology, ordering, and elapsed analysis. Ambiguous/nonexistent API input requires an explicit offset.

2. Successful streaming Chat​

stream=true; HTTP 200 starts first, and successful terminal delivery establishes completed. Failure after start can still have HTTP 200, so inspect status too. Final loop information is in Chat terminal and Runs detail.

3. Chat waiting for HITL​

Usage is hitl_pending, HTTP 200, no error. A pending row shares the session ID. Resume preserves chat and creates a new request ID. Even after compaction, pending row/checkpoint interrupt—not summary prose—decides resume.

4. Repeated request​

Same scope/request ID does not execute again. The original accepted row stays; a separate duplicate attempt has dedup_result=duplicate, status=rejected, HTTP 409, and a safe duplicate error. Frequent rows may indicate duplicate UI submits or incorrectly reused retry IDs.

5. Invalid identity/UUID​

Missing orch, blank/placeholder user, or nil IDs return 400 invalid_identity; malformed UUID schema returns 422 validation_error. Dots are not validated. Usage is not_applied/rejected with the safe error, without model/RAG/MCP work.

6. Previous stream still active​

Session conflict is rejected, HTTP 409, with dedup_result=accepted or not_applied because the ID may be new. Wait for the previous stream. Duplicate means request-ID collision; conflict means concurrent work in one conversation.

7. Manifest, Probe, Search​

These create no Usage rows. Search X-Request-Id and Probe metadata.x_request_id still correlate responses/logs, but do not identify Chat ledger rows. Repeated Probe payloads both execute workload; there is no separate idempotency store for these APIs.

Native tools are ls, read_file, write_file, edit_file, glob, grep, and subagent task. Writes/edits are allowed only in workspace. No shell/execute. Tool permissions and backend traversal/read-only checks both enforce boundaries. Runtime is not an arbitrary model-created workspace.

Quota measures UTF-8 bytes. Default per-file 512 KiB/thread 2 MiB failures return workspace_quota_exceeded without silently overwriting files. Both settings must be positive and file limit must not exceed total.

Workspace files do not replace delivered answers. The prompt requires results in chat. Disabled entries remain configuration but disappear from loading, injection, manifest, and execution tracing. Use includeInManifest=false to hide only Router inventory while retaining runtime execution. Evidence retains actual arguments/results, excluding framework input.runtime; nesting identifies the owning Agent.

Access metadata is app-owned and never sent to MCP. Absent/empty access is public; non-empty groups require intersection for exposure and execution.

Injection is separate: it transfers normalized request-body or inbound-header sources into explicit body/header destinations for already permitted tools. All four directions are expressible. Header destinations apply only to HTTP/SSE MCP; write downstream names such as X-User-Id, not snake_case source names. Header comparison is case-insensitive; configuration consistently uses readable hyphenated names.

Does requestScopedInjection grant permissions?​

No. It transfers data during an already authorized invocation; it cannot expose or execute a forbidden MCP. A body injection can supply RAG groups; a header injection can forward correlation metadata.

Stdio call timeout is enforced by Runtime, not an SDK connection argument. HTTP uses it at adapter connection and tool wrapper. Independent per-server discovery budget prevents one slow server from blocking preparation indefinitely. Manifest is partial best-effort; first Chat discovery also isolates failed servers, with no required retriever-name contract.

Chat retains per-server last-known-good definitions. The first request after 600 seconds from completed discovery refreshes registered candidates. Successful servers replace their whole set, including authoritative empty lists. Failed servers retain definitions/state. Changed name/description/schema triggers graph compilation; a candidate is adopted atomically with definitions/state. Failed compile preserves the old graph and advances the completed-attempt clock. Unchanged fingerprints still adopt recovery state. No scheduler/additional TTL/env exists.

Typed connection/session failures count at server scope; per-tool timeout, confirmed stale tool/schema, and backend errors count at tool scope. Two consecutive failures block exposure and dispatch. Invalid arguments, normal empty success, cancellation, and HITL do not count. Classified external failures do not consume global mistake budget, while repeated forbidden calls and execution limits remain. Shared state requires the same connection/authentication scope. Fixed built-in RAG/DS connections retain failures and blocks across requests without resetting on correlation arguments. Custom dynamic request injection retains request-local isolation. Active requests pin definitions and block state; late results cannot poison a newer generation. Adopted discovery success permits new requests; failure keeps blocks until the next 600-second opportunity.

Why can Manifest and Chat have different MCP tools?​

Manifest is static per-server best-effort inventory. Disabled, hidden, or failed servers may be absent while siblings remain. Chat combines currently permitted enabled servers with last-known-good state; an initially failed server is omitted without requiring a particular retriever. Timing, request permissions, and block state can therefore produce different lists. Manifest has no per-user group body, so restricted Skill/Agent descriptions may appear; Chat filters actual exposure again.

Stdio python/python3 resolves to the API's interpreter, so a host virtualenv also runs child MCP with its dependencies. Explicit custom interpreter paths/launchers are retained and must contain required dependencies. sse_read_timeout measures next-event silence, not total execution; default assets use adapter 300 seconds.

note

Manifest visibility follows enabled/includeInManifest/discovery. Per-user runtime visibility follows access.permission_groups independently.
