Usage Guide

This guide explains the values callers must prepare for each Agent Runtime request. Start with Quickstart to make a first call, and use API reference for endpoint contracts.

Start here​

Chat uses an OpenAI-compatible payload with additional orch metadata. messages contains the conversation the model reads. orch supplies session identity, permissions, search scope, and duplicate-request information.

tip

Call GET /v1/models and GET /v1/indices first, then use the values allowed by the deployment in your Chat request.

Request body
{
  "model": "<model-id-from-catalog>",
  "stream": true,
  "messages": [
    {"role": "user", "content": "Explain the causes of deployment delays and recommended actions."}
  ],
  "orch": {
    "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
    "x_request_id": "896cd7ad-8e3c-4c85-b918-a294d133c44e",
    "identity": {"user_id": "employee.one", "send_system_name": "ds_assistant"},
    "rag_params": {"index": "rag-index", "permission_groups": ["example-team"]}
  }
}

messages​

messages is the user-visible conversation. At least one message is required; at most one system message is allowed. Its text is an auxiliary instruction for the current HTTP request's Main Agent. It cannot override the service prompt, runtime context such as Memory and the current time, identity, security, authorization, tools, or evidence policy.

The system message is excluded from graph messages and checkpoint history. It does not carry over to another request with the same chat_id unless sent again. HITL resume uses only the current resume request's instruction. Multipart content joins text parts in order and ignores images as instructions; blank text supplies no instruction. It is not automatically forwarded to subagents, the Turn Evaluator, or the conversation compactor. Streaming does not change these rules.

Clients may resend the full user-visible transcript for the same chat_id. The server excludes the prefix matching its checkpoint and appends only the new suffix. Editing old messages can break prefix matching and duplicate history, so keep previous messages intact. Retrying a failed request with the same transcript does not append a user message already in the checkpoint. After a successful response, the same sentence sent as a new request is a new user occurrence.

A large transcript is not rejected merely for exceeding the compaction trigger. Native compaction uses the model profile's capacity to produce a summary and recent tail so execution can continue. Missing historical details can be retrieved from thread-private runtime archives; clients do not manage /runtime paths. This cannot repair a single current user request larger than the provider context: split that input into smaller requests.

An ask_user call can define 1–3 questions, each with 2–4 options and at most one recommendation. Questions are answered one at a time. Non-blank free text outside the options is passed through unchanged.

max_tokens, max_completion_tokens, temperature, top_p, frequency_penalty, seed, stop, and generation_config are accepted for client compatibility but discarded before validation. They cannot change Main Agent or Internal LLM settings. The caller-controlled transport setting is stream.

user_id​

user_id separates user sessions, Usage, tool context, long-term Memory, and past conversation ownership. Identity validation and ownership remain enforced with authentication OFF. Personalization OFF skips automatic Memory loading, injection, and storage; it preserves records, summaries, history access, and explicit deletion of the user's own Memory.

With personalization ON, Main tools confirm explicit additions/corrections. A deletion turn may retain unrelated durable facts while excluding deletion targets. Internal management/lookup labels are hidden; narration and answers remain model-generated.

danger

Provide meaningful requester identifiers in user_id, chat_id, and x_request_id. Only surrounding whitespace is stripped from user_id. Blank values and the literal "user_id" return 400 invalid_identity; employee, employee.one, and employee.one.test are all valid. Missing orch or nil UUIDs fail identity validation. Malformed UUID syntax instead returns 422 validation_error from schema validation.

send_system_name​

orch.identity.send_system_name records the Usage source and selects the Chat authentication path when CALLER_AUTH_ENABLED=true. OFF skips Key verification, binding checks, and trusted classification.

Callersend_system_name
Trusted internal callerExact system name permitted by the operator
System / Sub frontendIssued Key's binding base name; append _test for test calls
Personal APIOmitted, null, blank, or exact api

medic_test binds to medic. The _test suffix is removed only after the exact trusted-sender check. See Developer guide for that boundary.

A matching active Key permits a system without an additional allowlist. A personal Key paired with a System sender returns 403 api_key_binding_mismatch; personal clients must omit the sender or send exact api.

permission_groups​

Groups are authorization data, not display labels. They affect RAG document access and MCP, Skill, and Agent exposure and execution.

Trusted callers use the requested groups unchanged. Sub frontends and personal API callers authenticate the Key and binding, query the Permission API with the normalized user_id, and merge every string value with requested groups using a set() union. Allowing additional caller-supplied personal API groups is intentional.

If PERMISSION_API_URL is blank, both API queries and cache access are skipped and request groups are used. A configured API failure does not switch the feature OFF. Empty groups do not grant all permissions; public assets follow their declarations.

warning

Group order is irrelevant. Whitespace, case, and Unicode are not normalized. The queried user_id is not implicitly added as a group; send it explicitly if needed.

index​

index selects a search corpus. Query the catalog for the deployment's allowed values.

info

The value is the backend index name, not a UI label. A UI can show a friendly name but must send the value returned by /v1/indices.

Request
curl "$AGENT_RUNTIME_API_BASE/v1/indices"
Response
["rag-index"]

Chat accepts one index or comma-separated indices in one string. Blank selects all public indices configured by RAG_INDEX. If built-in search is OFF or there is no public RAG index, /v1/indices returns [] and direct Search/Probe return 404 feature_disabled. Chat and independent custom MCP servers remain available. A configured upstream failure is distinct from OFF and from a successful empty result.

One index
{"rag_params": {"index": "rag-index", "permission_groups": ["example-team"]}}
Multiple indices
{"rag_params": {"index": "rag-index,example-index", "permission_groups": ["example-team"]}}
All indices
{"rag_params": {"index": "", "permission_groups": ["example-team"]}}

chat_id​

This is the conversation thread ID for LangGraph checkpoints, hitl_pending, HITL resume, same-session single-flight protection, and the internal /workspace.

tip

Store chat_id with each conversation record so reopening, follow-up questions, and HITL answers continue the same conversation.

Python
import uuid

chat_id = str(uuid.uuid4())
User actionchat_id
Start a conversationNew UUID
Follow up in that conversationPreserve the UUID
Answer HITLPreserve the UUID
Reopen a conversationUse its stored UUID

Internal working files persist only for the same user_id:chat_id. A new chat cannot see the old workspace. Files are not downloadable artifacts; the result is delivered in the assistant message.

A concurrent request for the same session may return 409 session conflict. Wait for the previous stream to end before sending another question.

HITL spans multiple HTTP requests but belongs to one interaction. Clients only need to preserve chat_id and create a new x_request_id. The server manages each request's run_id, the initial interaction_id, previous parent_run_id, and zero-based phase_index.

x_request_id​

This is the caller's per-request idempotency/correlation ID. Internally and in PostgreSQL it is normalized to request_id.

warning

Create a new UUID for every new user question. Reusing it may return 409 duplicate_request. A network retry may reuse it to prevent duplicate work, but the server does not replay the earlier response: it closes the retry with 409.

Python
import uuid

x_request_id = str(uuid.uuid4())
Situationx_request_id
New questionNew UUID
Network retry of the same questionReuse to prevent duplicate work and handle 409
New question after stoppingNew UUID
Submit a HITL answerNew UUID
Refresh may resubmit a requestPrevent duplicate submission in the UI

A previously used ID within the same deduplication scope returns 409 duplicate_request, meaning the workload was not executed twice.
