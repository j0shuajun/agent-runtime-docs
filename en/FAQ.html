FAQ

Does empty orch.rag mean no search occurred?​

No. Chat terminal orch.rag.source_urls, contexts, and doc_images remain empty for compatibility. Find the run_id using /v1/runs, then request GET /v1/runs/{run_id}/evidence for retrieval and tool evidence. Answer citations are in the assistant message itself.

Will retrying x_request_id replay the response?​

No. Reusing an ID already accepted within the same user_id:chat_id returns 409 duplicate_request without executing the workload twice. This is not an idempotent response cache.

Why does Chat accept blank index while Search Proxy rejects blank index_name?​

The contracts differ. Blank Chat orch.rag_params.index selects all configured public RAG indices. Search Proxy requires an explicit validated search boundary and rejects blank names, wildcards, and non-allowlisted values with 422.

Why can Chat fail when /health returns 200?​

/, /health, and /metrics are shallow process checks. They do not probe PostgreSQL, RAG, the LLM gateway, or MCP on each request. Check the public error code, correlated pod logs, and dependency health separately.

Can information persist across a new chat_id?​

With personalization ON, the same user's long-term facts and preferences may be used in a new chat. Memory is user-scoped and exposed read-only at /memories/MEMORY.md. Actual messages, HITL, and /workspace are scoped to user_id:chat_id. Other users' Memory and conversations are inaccessible.

OFF blocks automatic Memory reads, injection, writes, and ordinary file access. It preserves existing Memory, records, summaries, checkpoints, and history access. Explicit full or partial deletion of the user's own Memory remains available. Partial deletion removes only relevant phrases and preserves the remaining text and original record timestamps.

With personalization ON, explicit additions/corrections use a Main tool and actual results. An unrelated durable fact supplied with deletion can still be remembered; the deleted target is excluded. Memory/history/private recovery labels are hidden, and the model generates its own response wording.

Can system, temperature, or max_tokens change Agent policy?​

They cannot change service policy. One system message may provide lower-priority auxiliary instructions to the current request's Main Agent. It is excluded from graph messages and checkpoints and is not automatically inherited by subagents, the Evaluator, or compactor. temperature, top_p, max_tokens, max_completion_tokens, frequency_penalty, seed, stop, and generation_config are accepted for compatibility but discarded before validation. Callers choose the response transport using stream.

Can another user or chat see Agent files?​

No. /workspace is private to user_id:chat_id. PostgreSQL checkpoints preserve it across requests and API processes for that thread, but not for a new chat or another user. Deployment assets/skills and assets/agents are separate shared sources. Only permitted assets appear read-only under /skills and /agents; they are not copied into the workspace.

Can users download files created by the Agent?​

No. /workspace holds internal drafts and analysis; there is no download endpoint or artifact card. Requested results must appear in the final chat body. File work may appear as [Tool] write_file; details OFF hides that notice but keeps execution.

Can the Agent run a shell or read real pod files?​

No. The filesystem is a default-deny virtual view of /workspace, /runtime, /memories, /skills, and /agents, not the host /. /runtime is a private framework namespace. Models can target only exact conversation-provided paths under /runtime/conversation_history/<artifact> and /runtime/large_tool_results/<artifact>. Writes, root browsing, arbitrary namespaces, relative paths, and traversal are denied. /memories/MEMORY.md is the current user's read-only long-term Memory and is unavailable for ordinary access with personalization OFF. Shell/execute, assets/mcp_server.json, and unrouted host files are not exposed. Backend and permission checks deny writes to /skills, /agents, and /memories.

How do I inspect RAG results used in Chat?​

Find the user's run_id in /v1/runs, then request its evidence. Observations contain actual execution inputs and outputs. Look for type="tool" with the search tool name: input holds the query and output holds retrieved results. Results remain sanitized JSON-safe values rather than arbitrarily truncated previews.

How do I identify the Agent that executed a tool or Skill?​

Read the nested evidence tree. Each Main/subagent Agent's observations contains its models, tools, Skills, and nested agents in execution order.

Search executed by a subagent
{
  "type": "agent",
  "name": "researcher",
  "observations": [
    {
      "type": "tool",
      "name": "rag_search",
      "input": {"query": "causes of deployment delays", "index": "rag-index"},
      "output": {"results": [{"title": "Deployment Delay Overview", "score": 0.82}]}
    }
  ]
}

This tool belongs to researcher because it is nested under that Agent. Skills and models use the same ownership structure; clients need not reconstruct a public tree by joining separate IDs.

How are MCP, tool, and RAG permissions applied?​

Authorization uses the effective request's orch.rag_params.permission_groups.

ResourceEnforcement
RAG retrievalGroups are sent to the backend to restrict searchable documents.
MCP server/toolA declared non-empty access.permission_groups must intersect request groups. Absent or empty declarations are public.
SkillThe same group intersection rule applies.
AgentThe same group intersection rule applies.

What are permission_groups?​

They are exact strings used for RAG, MCP, Skill, and Agent authorization. Trusted callers use request groups directly; System/Sub frontends and personal API callers merge them with Permission API value fields queried using the normalized user_id. Additional personal API groups are intentionally allowed.

A blank Permission URL skips API and cache access and uses request groups. A configured failure does not become OFF. Authentication OFF still preserves groups and ownership. Group comparison uses an unordered exact-string set(); do not assume normalization of case, whitespace, or Unicode.

Where are groups used?​

They determine both searchable documents and visible MCP servers, Skills, and Agents.

{
  "orch": {
    "rag_params": {
      "permission_groups": ["EXAMPLE_READERS", "EXAMPLE_REVIEWERS"],
      "index": "rag-index"
    }
  }
}

These are example groups, not mandatory fixed values. Send the actual signed-in user's groups from your permission system.

What does index select?​

It selects candidate search corpora. A UI sends its selected value; direct API clients send orch.rag_params.index or Search index_name.

Selecting an index does not make every chunk available to generation. The backend also intersects each uploaded chunk's groups with request groups. For example, rag-a,rag-b with only example-team can search only chunks in those indices that permit example-team. An index in a payload or database is not proof that all its chunks contributed to the answer.

How do groups affect RAG search?​

Search tools forward request groups to the RAG API. A user with only example-team receives only documents permitted to that group. Runtime does not expand permissions or append unauthorized documents after receiving results.

How are MCP, Skills, and Agents shown or hidden?​

An absent or empty access.permission_groups is public. A non-empty declaration requires at least one exact intersection with request groups; otherwise the asset is not a model candidate. For example, an MCP requiring restricted-team is absent from a request containing only example-team.

Does registering a new System require redeployment?​

With authentication ON, issue an active Key with binding_field=send_system_name and the base system name as binding_value. No separate allowlist or redeployment is needed. A medic_test caller binds its Key to medic.

OFF accepts calls without Key checks and returns 404 feature_disabled from Key management. Existing Key records are retained.

Can several Keys share a binding?​

Yes. Several Keys may be active simultaneously and have independent expiry, verification, and revocation. For rotation, POST the new Key, switch the consumer, then DELETE the old Key. POST does not revoke existing Keys.

Can PATCH reactivate an expired or revoked Key?​

No. PATCH changes expires_at only on an active Key. Expired/revoked Keys return 409 api_key_not_active; POST a new credential. Repeated DELETE on a revoked Key is a 204 no-op and preserves the original revoked_at.

Can I send a large transcript in the same conversation?​

Yes. Runtime skips the checkpoint-matching prefix and adds only the new suffix. Native compaction creates a summary projection and recent tail according to model capacity. Missing details can be recovered internally using grep and targeted read_file on actually preserved thread-private /runtime/conversation_history/** archives. Clients do not manage these paths. Merely exceeding a compaction trigger does not reject the transcript; retrying a failed request also avoids duplicating checkpointed input.

If the single latest user message exceeds provider context capacity, compaction of history cannot fix it. Split it and keep chat_id with a fresh x_request_id.

What remains when detailed progress is OFF?​

STREAM_PROGRESS_DETAILS_ENABLED=false hides Tool/MCP, Skill/Agent, processing, and HITL labels. Answer text, heartbeat, compaction, actual HITL questions/options, and required errors remain. Execution, persistence, observability, and HITL remain active. Raw model reasoning is never exposed, even with details ON.

Do repeated MCP failures stop the conversation?​

Initial discovery failure of a valid server excludes only that server. Classified invocation failures return as tool results; two consecutive failures block the affected tool or server from both exposure and dispatch. Invalid arguments, successful empty results, cancellation, and HITL do not count. Existing safeguards against repeating unavailable calls and exceeding execution limits remain.

The first request after 600 seconds from completed discovery retries registered servers. Successful discovery replaces the full list/definitions; an authoritative empty list removes tools. Failure preserves the last known good list and blocked state. Adopted recovery permits new requests; active requests retain their pinned definitions and block state. Configuration-file changes require a restart.

Where do I change language and timezone?​

DEFAULT_LOCALE=ko|en selects server notices; TIMEZONE selects time interpretation and presentation. Defaults are ko and Asia/Seoul. Notice-language changes require restart, but TIMEZONE is fixed at first deployment. Preserve existing Korean records; deploy other regions independently. Model answers, external text, and machine-readable fields are not automatically translated. Docusaurus has its own language menu, independent of server settings. Documentation-only DOCS_ROOT_LOCALE=ko|en selects its deployment root, default ko; both languages are built. Naive time input uses the deployment zone. Ambiguous/nonexistent DST times require an explicit UTC offset.
