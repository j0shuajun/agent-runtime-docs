API Key Management

These internal operator endpoints issue, list, update expiry, and revoke Binding API Keys used by System/Sub frontends and personal API clients.

CALLER_AUTH_ENABLED=false disables them with 404 feature_disabled, retains existing Key records, and skips Chat Key verification.

danger

There is no separate application credential for these endpoints. Ingress/network policy must restrict /internal/* to authenticated operators.

Common identifiers​

GET uses a key_ref query parameter; PATCH and DELETE use {key_ref} in the path. Both accept:

UUID key_id
07da0100-661f-405a-be4f-3198a631438e

22-character public_key_id
B9oBAGYvQFq-TzGYpjFDjg

public_key_id is the internal UUID's 16 bytes encoded as unpadded Base64URL. It is public, not a secret. Both formats must pass canonical round-trip validation.

warning

The complete sk-<public_key_id>.<secret> cannot be a URL identifier. It returns 422 invalid_key_reference to keep secrets out of URLs and access logs.

The full Key is 69 characters: sk-<22-character public_key_id>.<43-character secret>. PostgreSQL stores the UUID and an HMAC-SHA256 hash computed with a dedicated HKDF key derived from ENCRYPTION_MASTER_KEY; it stores neither the full Key nor secret.

Chat strips surrounding whitespace from x-api-key before format validation. Internal whitespace, invalid prefix/length/Base64URL, and secret mismatch still return 401 invalid_api_key.

Binding rules​

Usagebinding_fieldbinding_valueChat comparison
Personal APIuser_idOpaque identity such as employee or employee.oneorch.identity.user_id
System / Sub frontendsend_system_nameBase name such as medicSender with final _test removed

System bindings reject whitespace, the _test suffix, and reserved values api and invalid_send_system_name. Test calls also use the base-name Key.

1. Issue a Key​

POST /internal/v1/api-keys
Content-Type: application/json
Personal Key request
{
  "binding_field": "user_id",
  "binding_value": "employee.one",
  "expires_at": "2027-08-20 18:30"
}

For a System Key use binding_field="send_system_name" and a base name without _test, such as binding_value="medic".

Success returns 201 Created:

{
  "key_id": "07da0100-661f-405a-be4f-3198a631438e",
  "public_key_id": "B9oBAGYvQFq-TzGYpjFDjg",
  "api_key": "sk-B9oBAGYvQFq-TzGYpjFDjg.GSaZ5hDpQx2vU8mR1nC7eL4tK9wY6aF3jN0sVbHcXEI",
  "binding_field": "user_id",
  "binding_value": "employee.one",
  "issued_at": "2026-08-20T21:00:00+09:00",
  "expires_at": "2027-08-20T18:30:00+09:00"
}

The raw api_key appears only in this response. POST adds one credential without revoking Keys for the same binding or limiting their active count.

Key A active
POST Key B
Key A active + Key B active

For uninterrupted rotation, issue a new Key, verify the consumer switched, then DELETE the old Key. Concurrent issuance leaves each successful Key independently active.

2. Retrieve Keys​

One GET endpoint returns a list without key_ref, or one Key with it.

List and binding filters​

GET /internal/v1/api-keys
GET /internal/v1/api-keys?binding_field=user_id
GET /internal/v1/api-keys?binding_value=employee.one
GET /internal/v1/api-keys?binding_field=user_id&binding_value=employee.one

The filters may be separate or combined. The array contains no raw Key or secret_hash.

[
  {
    "key_id": "07da0100-661f-405a-be4f-3198a631438e",
    "public_key_id": "B9oBAGYvQFq-TzGYpjFDjg",
    "binding_field": "user_id",
    "binding_value": "employee.one",
    "issued_at": "2026-08-20T21:00:00+09:00",
    "expires_at": "2027-08-20T18:30:00+09:00",
    "revoked_at": null,
    "status": "active"
  },
  {
    "key_id": "another-key-uuid",
    "public_key_id": "another-public-key-id",
    "binding_field": "user_id",
    "binding_value": "employee.one",
    "issued_at": "2026-07-20T10:00:00+09:00",
    "expires_at": "2027-07-20T10:00:00+09:00",
    "revoked_at": null,
    "status": "active"
  }
]

Retrieve one Key​

GET /internal/v1/api-keys?key_ref=07da0100-661f-405a-be4f-3198a631438e
GET /internal/v1/api-keys?key_ref=B9oBAGYvQFq-TzGYpjFDjg

Both formats return the same record:

{
  "key_id": "07da0100-661f-405a-be4f-3198a631438e",
  "public_key_id": "B9oBAGYvQFq-TzGYpjFDjg",
  "binding_field": "user_id",
  "binding_value": "employee.one",
  "issued_at": "2026-08-20T21:00:00+09:00",
  "expires_at": "2027-08-20T18:30:00+09:00",
  "revoked_at": null,
  "status": "active"
}

Combining key_ref with a binding filter returns 422 validation_error because single-record selection conflicts with list filtering.

3. Update expiry​

PATCH /internal/v1/api-keys/07da0100-661f-405a-be4f-3198a631438e
PATCH /internal/v1/api-keys/B9oBAGYvQFq-TzGYpjFDjg
Content-Type: application/json
{"expires_at": "2028-08-20 18:30"}

Only expires_at can change. The response includes both identifiers, binding, deployment-zone timestamps, and calculated status. The Key must be active at request time; expiry may be shortened or extended if it remains after now and issued_at.

Expired/revoked Keys return 409 api_key_not_active without changing expiry. The storage UPDATE enforces the same condition so concurrent DELETE or expiration cannot reactivate a credential. Issue a new credential using POST.

4. Revoke a Key​

DELETE /internal/v1/api-keys/07da0100-661f-405a-be4f-3198a631438e
DELETE /internal/v1/api-keys/B9oBAGYvQFq-TzGYpjFDjg

Success is 204 No Content. The row is retained; the first DELETE sets revoked_at. Repeated DELETE is a no-op preserving that timestamp. Revoking an expired Key preserves expiry and changes status to revoked. Verification is not cached, so the next Chat request returns 401 api_key_revoked.

Status calculation​

There is no stored status column. Reads calculate:

revoked_at != NULL → revoked
expires_at <= now → expired
otherwise         → active

Active means revoked_at IS NULL AND expires_at > now; revoked takes precedence.

Time input and display​

Naive input uses TIMEZONE; responses use that zone's offset. Default Asia/Seoul is +09:00. Explicit offsets preserve the instant and only change display. Ambiguous/nonexistent local DST input is rejected; supply an explicit offset.

2027-08-20
2027-08-20 18:30
2027-08-20T18:30
2027-08-20 18:30:45
2027-08-20T18:30:45.123456
2027-08-20T09:30:00Z
2027-08-20T18:30:00+09:00

PostgreSQL TIMESTAMPTZ preserves instants, though another DB client's session zone may display a different offset. Expiry and revocation comparisons use actual instants, including distinct occurrences of repeated DST wall times.

Common errors​

Invalid UUIDs, non-22-character public IDs, noncanonical Base64URL, and complete sk-... Keys return 422 Unprocessable Entity:

{
  "error": {
    "message": "key_ref must be a canonical UUID or public key ID",
    "type": "invalid_request_error",
    "param": "key_ref",
    "code": "invalid_key_reference"
  }
}

These messages show the English locale. DEFAULT_LOCALE changes controlled messages; type, param, and code remain stable. Valid identifiers absent from the database return 404 api_key_not_found. PATCH on an inactive Key returns 409 Conflict:

{
  "error": {
    "message": "Only active API keys can be updated.",
    "type": "invalid_request_error",
    "param": "key_ref",
    "code": "api_key_not_active"
  }
}

Legacy artk_<UUID>.<secret> credentials are neither issued nor accepted. Their secrets cannot be recovered from storage; issue new Keys and update consumers.
