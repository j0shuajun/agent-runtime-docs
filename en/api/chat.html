Chat

Start Agent execution with an OpenAI-compatible payload plus orch metadata for execution, identity, and search. Most user interfaces only need POST /v1/chat/completions.

warning

Another request while a stream for the same user_id:chat_id is active may return 409 session conflict. Wait for the stream to end or stop it before sending a question.

POST /v1/chat/completions​

Request
curl -N "$AGENT_RUNTIME_API_BASE/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model-id-from-catalog>",
    "stream": true,
    "messages": [
      {"role": "user", "content": "Explain the causes of deployment delays."}
    ],
    "orch": {
      "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
      "x_request_id": "896cd7ad-8e3c-4c85-b918-a294d133c44e",
      "identity": {
        "user_id": "employee.one",
        "send_system_name": "ds_assistant"
      },
      "rag_params": {
        "index": "rag-index",
        "permission_groups": ["example-team"]
      }
    }
  }'

Caller authentication and effective groups​

The following classification applies with CALLER_AUTH_ENABLED=true. OFF skips Key verification, binding, and trusted classification, while preserving user/UUID validation, sessions, ownership, and permissions. A blank PERMISSION_API_URL skips API/cache access and uses request groups. A configured failure does not become OFF.

CallerClassificationx-api-keyEffective groups
Trusted internalExact configured trusted senderNot requiredRequest groups
System / Sub frontendNon-admin, non-reserved senderActive send_system_name binding to base name after final _test removalRequest + Permission API value
Personal APIOmitted, null, blank, or exact apiActive binding to normalized user_idRequest + Permission API value

Systems need no additional allowlist. A matching active Key permits calls as soon as it is issued. A personal Key paired with a System sender returns 403 api_key_binding_mismatch, without downgrading classification. Empty/placeholder identity is rejected before credential lookup, even for trusted callers. Trusted _test variants and reserved senders cannot bypass policy through a System Key. See API Key management for issuance, rotation, and lifecycle.

Sub/personal callers send x-api-key: sk-<22-character public_key_id>.<43-character secret>. Surrounding whitespace is stripped; the normalized token is 69 characters. Internal whitespace and legacy artk_ tokens return 401 invalid_api_key. Groups use exact Python set() comparison, without ordering or case/whitespace/Unicode normalization. Effective groups are identical in Usage, MCP injection, RAG, and asset exposure. The inbound Key is not forwarded to MCP or external tools.

Errors use {"error": {...}}. Rejected authentication never enters Agent execution, deduplication, or session locking. Chat Usage records it as status=rejected with the actual HTTP status/error and permission_groups=NULL, rather than a separate audit table.

Generation controls max_tokens, max_completion_tokens, temperature, top_p, frequency_penalty, seed, stop, and generation_config are discarded before validation. They do not alter Main/Internal LLM settings. stream selects transport.

Sender classification and optional orch.routing_check do not select a model or route; they determine Usage upstream_name.

Usage preserves extractable normalized user_id even after authentication failure; it does not replace it with invalid_user_id. Sender projection is independent. The stream shape is identical for enabled/disabled/absent routing_check; legacy routing notices are not sent.

Requester-provided system instruction​

At most one role="system" message may guide Main answer formatting/work in the current HTTP request.

Request-scoped instruction
{
  "messages": [
    {
      "role": "system",
      "content": "Start with the conclusion and use a table."
    },
    {
      "role": "user",
      "content": "Compare the two operating procedures."
    }
  ]
}

It does not replace the service prompt, Memory/current-time context, or mandatory identity/security/authorization/tool/evidence policy. Multipart text parts join in order; images are ignored as instructions and blank text supplies none.

The instruction is excluded from conversation/checkpoint state, so future requests and HITL resumes use only their own current instruction. Stream/non-stream are equivalent. Subagents, Evaluator, and compactor do not inherit it.

Usage records only Chat requests; Manifest, Probe, and Search create no rows here, so this table has no endpoint/operation columns. Missing orch, blank user, and literal "user_id" return 400 invalid_identity. Nil UUIDs also return 400; malformed UUID syntax returns 422 validation_error.

Streaming response​

Streaming response excerpts
data: {"choices":[{"delta":{"role":"assistant"},"finish_reason":null}],"agent":{"name":"Agent Runtime"}}

data: {"choices":[{"delta":{"reasoning_content":"Searching...\n"},"finish_reason":null}],"agent":{"name":"Agent Runtime"}}

data: {"choices":[{"delta":{"content":"Deployment delays are ..."},"finish_reason":null}],"agent":{"name":"Agent Runtime"}}

data: {"choices":[{"delta":{"content":""},"finish_reason":"stop"}],"orch":{"result_message":{"content":"Final answer"}},"loop":{"tool_calls":1,"model_calls":1,"stop_reason":"completed","duration_ms":800,"repeats_blocked":0,"compaction":{"occurred":false,"count":0,"cutoff_index":null}},"agent":{"name":"Agent Runtime"}}

data: [DONE]

Examples omit id, object, created, model, choice index, and terminal orch.rag for readability; actual responses include the common envelope. Every JSON event has the configured top-level agent.name. [DONE] is a non-JSON sentinel and has no Agent metadata. Comments, strings, and malformed JSON also receive no metadata; non-stream JSON is unaffected.

One standalone {"role":"assistant"} delta appears immediately before the first Main progress, content, or terminal event. Later chunks do not repeat it.

During LLM, MCP, graph, storage, or external waits, the wrapper sends visible reasoning_content heartbeat. This supports UIs that otherwise display an idle error after 60 seconds without visible content. Preparation wait carries into streaming; only post-filter transmitted text resets the idle clock. Heartbeat stops after terminal, HITL, error, or cancellation.

Details OFF hides Tool/MCP, Skill/Agent, processing, and HITL labels but preserves heartbeat, compaction, body, actual HITL questions/options, and required errors. Raw model reasoning is never exposed. DEFAULT_LOCALE=ko|en selects controlled notices without automatically translating model answers, external text, or machine fields.

Idle heartbeat
data: {"choices":[{"delta":{"reasoning_content":"Thinking...\n"},"finish_reason":null}],"agent":{"name":"Agent Runtime"}}

Do not append heartbeat to answer content. SSE comment keep-alive may supplement transport, but visible progress/idle handling uses the heartbeat delta.

note

If preparation exceeds the interval, heartbeat can precede assistant role. It signals continued waiting; role signals Main output start. Handle fields independently instead of assuming the first event is a role event.

Filesystem work uses ordinary tool progress:

data: {"choices":[{"delta":{"reasoning_content":"[Tool] write_file\n"},"finish_reason":null}]}

data: {"choices":[{"delta":{"reasoning_content":"[Tool] read_file\n"},"finish_reason":null}]}

Every terminal completes finish_reason/metadata with delta.content="" and never resends body. After partial text, an error fallback is another content delta:

Partial response followed by an error
data: {"choices":[{"delta":{"content":"I will begin the work."},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":"\n\nAn error occurred while processing your request."},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":""},"finish_reason":"error"}],"orch":{"result_message":{"content":"I will begin the work.\n\nAn error occurred while processing your request."}}}

Accumulated content equals terminal orch.result_message.content. Use the latter for verification/storage, not another display append.

When compaction occurs:

Compaction metadata
{
  "loop": {
    "compaction": {
      "occurred": true,
      "count": 1,
      "cutoff_index": 37
    }
  }
}

cutoff_index identifies the cumulative checkpoint boundary replaced in the summary projection. Summaries, archive paths, and raw history are excluded. Streaming sends a controlled compaction notice. After the cycle completes and Main content/tool/Skill/Agent work resumes, the next compaction can announce again. Summarizer bookkeeping, empty model events, and heartbeat do not rearm it. The notice is excluded from non-stream bodies and terminal artifacts; count remains actual.

Chunks from one Main model call concatenate unchanged. A later call's first valid text gets only the newlines needed for a blank-line boundary. The same assembler handles tool-separated answers, revisions, and HITL questions. Empty/tool-only calls create no blank block. SSE concatenation, terminal, non-stream, and stored body use the same composition.

Large routed history is not rejected merely at the trigger. Runtime deduplicates the checkpoint prefix, appends the suffix, and compacts history while continuing. Unresolved overflow after forced compaction ends streaming with finish_reason=error, loop.stop_reason=context_overflow. Split a current user message that itself exceeds provider capacity.

HITL(Human-In-The-Loop)​

HITL asks the user for information instead of completing the answer. HTTP 200 with finish_reason=hitl means awaiting input. Show the question and resume the same conversation. An ask_user call contains 1–3 questions, with 2–4 options for choice questions and at most one recommendation each. Questions interrupt/resume sequentially; non-blank free input is not coerced to an option label.

  1. Inspect finish_reason.
  2. On hitl, display question text.
  3. Resume with the same chat/user and a fresh request ID.
  4. Put the user's answer in messages[].content and hitl.answer.
FieldMeaning/handling
finish_reasonhitl means awaiting input, not completed.
message.contentDisplay non-stream question.
delta.contentAccumulate streaming question.
hitl.questionStructured question for labels/state.
hitl.question.optionsSuggested label, optional description, recommended; buttons/radio may supplement always-available free input.
current_index / totalCurrent position, e.g. 2 / 3.
reask_countBlank-answer reasks; 1 means shown again once.
hitl.idQuestion identifier; need not be resent on resume.

Streaming HITL​

Question text can arrive as ordinary content before terminal finish_reason=hitl.

Answer and resume​

Preserve chat_id and user_id and create a new x_request_id.

Resume request
curl -N "$AGENT_RUNTIME_API_BASE/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model-id-from-catalog>",
    "stream": true,
    "messages": [
      {"role": "user", "content": "Use the SOP-123 document."}
    ],
    "hitl": {
      "answer": "Use the SOP-123 document."
    },
    "orch": {
      "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
      "x_request_id": "fa9e0675-881d-4437-9d6b-a1d6e9c794ee",
      "identity": {
        "user_id": "employee.one",
        "send_system_name": "ds_assistant"
      },
      "rag_params": {
        "index": "rag-index",
        "permission_groups": ["example-team"]
      }

ValueRule
orch.chat_idPreserve the interrupted chat.
orch.identity.user_idPreserve the user.
orch.x_request_idNew ID; never reuse the prior phase ID.
messages[].contentStore the user's answer in conversation history.
hitl.answerResume answer, normally the same string.
streamResume supports either transport.

If message and hitl.answer differ, the latter resumes. If absent, runtime uses the first hitl.answers[], then the latest user message. Prefer explicit hitl.answer.

Non-blank input such as 2, B, option 2, but only the same project, or none of these; use the last three days stays intact. Main interprets it with the original question/options; clients must not discard conditions or force a closest option. A completed resume ends with stop:

Multiple questions​

A resume can return another HITL. Repeat the same flow. Every phase has a new run_id; Runs shares the initial interaction_id, previous parent_run_id, and zero-based phase_index. Clients do not create these. Langfuse shows one LangGraph trace per request, and Sessions show current user/assistant exchanges without duplicating old turns. Full model history is in that trace's ChatOpenAI child.

Second HITL question
{
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Please also provide the project ID."
      },
      "finish_reason": "hitl"
    }
  ],
  "hitl": {
    "kind": "ask_user",
    "id": "intr-123",
    "question": {
      "question": "Please also provide the project ID."
    },
    "questions": [
      {
        "question": "Which reference document should I use?"
      },
      {
        "question": "Please also provide the project ID."
      }
    ],
    "current_index": 1,
    "total": 2,
    "reask_count": 0,
    "required": true
  },
  "loop": {
    "stop_reason": "hitl"

}

Here current_index:1, total:2 is the second question. Blank input reasks once with reask_count:1; a second blank marks it unanswered and continues to the next question or Agent. Bounded best-effort uses actual answers only, never unanswered placeholders as user facts.
