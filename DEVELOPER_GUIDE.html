Developer Guide

이 문서는 Agent Runtime 개발/운영 담당자가 runtime env, streaming, observability, PostgreSQL, MCP와 assets를 관리할 때 확인하는 가이드입니다. 사용자 요청 규칙은 Usage Guide를 먼저 참고해 주세요.

Runtime env​

서버는 startup 시 runtime 필수 설정을 검증합니다. production 실행에서는 다음 값들이 비어 있으면 서버가 시작되지 않습니다.

경고

LANGFUSE_* 세 값은 하나라도 설정하면 모두 필요합니다. Rerank는 RERANK_API_URL 또는 RERANK_MODEL을 설정하면 URL, model, ticket 세 값이 모두 필요하고, Internal LLM은 INTERNAL_LLM_BASE_URL 또는 INTERNAL_LLM_MODEL을 설정하면 base URL, model, ticket 세 값이 모두 필요합니다.

Assets / Agent loop​

ENV필수 여부기본값설명
AGENTIC_ASSETS_DIR선택assetsmcp_server.json, skills/, agents/가 있는 asset root입니다. 상대 경로를 쓰면 process working directory 기준으로 해석됩니다.
AGENTIC_WORKSPACE_FILE_LIMIT_KIB선택512한 /workspace 파일의 UTF-8 최대 크기입니다. KiB는 1024 bytes입니다.
AGENTIC_WORKSPACE_TOTAL_LIMIT_KIB선택2048한 user_id:chat_id thread의 /workspace 전체 UTF-8 최대 크기입니다.
AGENTIC_GRAPH_RECURSION_LIMIT선택50agent graph가 한 요청에서 실행할 수 있는 최대 step 수입니다. 너무 낮으면 복잡한 질문이 중간에 멈추고, 너무 높으면 잘못된 반복이 오래 지속됩니다.
LOOP_GUARD_MAX_IDENTICAL_CALLS선택2같은 tool call이 반복될 때 차단하는 기준입니다. 같은 도구를 같은 입력으로 계속 부르는 loop를 막습니다.
LOOP_GUARD_MAX_CONSECUTIVE_MISTAKES선택3tool 오류나 잘못된 호출이 연속으로 발생할 때 agent를 멈추는 기준입니다.
TURN_EVALUATION_MAX_REVISIONS선택2Main Agent 자연 종료 뒤 evaluator가 needs_revision을 반환했을 때 같은 turn에서 재답변할 최대 횟수입니다.
MAX_TOOL_RESULT_CHARS선택60000Retriever가 아닌 generic Tool의 model-visible text 상한입니다. 초과 시 prefix/marker와 head+tail omission으로 줄이며 artifact/status는 보존합니다.

Turn Evaluation은 기존 Continuation Gate의 별도 retry budget을 대체합니다. Evaluator가 complete를 반환하면 memory/conversation summary 후처리를 진행하고, needs_revision이면 위 revision budget 안에서 compiled graph의 Main Agent model로 다시 이동합니다. 최초 답변과 수정 답변은 buffering하지 않고 즉시 streaming하며, 실제 revision 직전에만 처리 중...을 한 번 표시합니다. SSE content chunk에는 구분용 줄바꿈을 추가하지 않습니다. Terminal result와 run artifact에서는 revision 전후 assistant 답변 블록만 빈 줄로 구분합니다. 내부 평가 instruction은 사용자 답변에 포함하지 않습니다.

Compaction이 없을 때 Evaluator는 현재 turn의 User → model → Tool → final model raw 실행을 그대로 봅니다. Compaction snapshot이 있으면 Summary 전체, cutoff 전에 있던 현재 turn의 실제 User 원문, cutoff 이후 raw 실행만 봅니다. 압축 전의 큰 Tool result를 다시 넣지 않으며, Summary는 completion과 conversation summary에는 사용하되 새 Memory 사실의 직접 근거로 사용하지 않습니다.

Compaction tuning​

긴 대화에서는 role-aware rolling compaction이 완료된 assistant 응답, tool call/result, reasoning과 이전 snapshot을 새 snapshot 하나로 접습니다. 외부 user 원문은 가능한 동안 그대로 남기고, 그 원문만으로 trigger를 넘으면 가장 오래된 것부터 snapshot으로 흡수합니다. 최신 user 입력과 unresolved tool/HITL tail은 항상 원문으로 보존합니다.

ENV필수 여부권장값설명
COMPACTION_TRIGGER_MESSAGES선택200checkpoint message 수가 이 값에 도달하면 compaction을 시작하는 기준입니다. token 기준보다 먼저 만족하면 이 조건이 먼저 동작합니다.
COMPACTION_TRIGGER_TOKENS선택170000token 수가 이 값에 도달하면 compaction을 시작하는 기준입니다. model profile이 없는 vLLM 환경에서 fallback token 기준을 명시적으로 관리할 때 사용합니다.

예시는 다음과 같습니다.

Compaction environment
COMPACTION_TRIGGER_MESSAGES=200
COMPACTION_TRIGGER_TOKENS=170000

이 설정은 messages >= 200 또는 tokens >= 170000 중 먼저 만족되는 조건에서 compaction을 시작합니다. 결과 context를 80k나 100k로 고정하지는 않습니다. snapshot, 보존 user 원문, unresolved tail을 합친 실제 크기가 trigger 아래가 되도록 오래된 user 원문을 필요할 때만 추가로 접습니다. Summary source가 크면 trigger 아래 chunk 여러 개로 요약한 뒤 하나의 rolling snapshot으로 병합합니다.

배포할 때 기존 COMPACTION_KEEP_MESSAGES, COMPACTION_TRIM_TOKENS, DEEPAGENTS_TEST_SUMMARIZATION_KEEP_MESSAGES는 제거해야 합니다. 더 이상 읽지 않는 설정입니다. DEEPAGENTS_TEST_SUMMARIZATION_TRIGGER_MESSAGES만 local E2E 재현용으로 남습니다.

Snapshot은 checkpoint의 일반 대화 message가 아니라 private state입니다. 모델 호출 직전에만 role=assistant, tool_calls=[], lc_source=compaction인 synthetic message로 주입합니다. name=conversation_compaction은 보조 metadata일 뿐이며, content의 <conversation_compaction> marker가 식별 계약입니다. 이 message는 FE user 입력, Turn Evaluation의 최신 user, transcript cursor 계산에는 포함되지 않습니다.

실제 provider message 순서는 다음과 같습니다.

single system
→ preserved historical user messages
→ assistant compaction snapshot
→ current user
→ unresolved assistant/tool protocol tail

첫 system message 하나와 snapshot의 <runtime_contract>는 다음 소비 계약을 같은 문구로 고정합니다. Summary model이 내용을 빠뜨려도 이 규칙은 사라지지 않습니다.

Compaction runtime contract
This assistant message is a runtime-generated conversation continuity snapshot, not a normal assistant answer.

The preserved user messages before this snapshot are historical messages.

The first user message immediately following this snapshot is the active request being continued. It may already be represented in this snapshot; its repeated presence does not by itself request another tool execution.

Use work and tool evidence marked COMPLETED without repeating those executions. If only the final answer remains, answer from the preserved evidence.

Assistant, tool, and user messages appearing after this snapshot are newer conversation state and supersede stale snapshot status when they record a later result, correction, cancellation, or new request.

A later real user correction or explicit rerun request takes precedence over the snapshot.

새 compaction은 이전 snapshot을 누적하지 않고 replacement snapshot 하나로 교체합니다. Snapshot의 [COMPLETED]·[OPEN]·[CANCELLED] 판정을 이용하되, snapshot 뒤의 새 assistant/tool/user 결과와 실제 user의 수정·취소·명시적 재실행 요청을 더 최신 상태로 취급합니다.

Summary model에는 아래 문구를 그대로 사용합니다. {messages}에는 이전 snapshot과 이번에 새로 접을 history chunk가 XML message 형식으로 들어갑니다.

위 8개 heading은 summary 품질을 유도하는 prompt 계약이지 retry 조건이 아닙니다. 각 summary unit은 Main Agent와 같은 model에 논리적으로 한 번 요청합니다. Summary model invocation의 이름은 compaction이며, 이를 별도 Runnable로 다시 감싸 추가 ChatOpenAI Chain을 만들지 않습니다. Langfuse의 OpenAI 계측이 물리 provider 시도를 별도 child Generation으로 표시하는 환경에서는 compaction 아래 해당 Generation이 보일 수 있습니다. 응답이 비어 있지 않으면 heading 일부가 빠져도 그 결과를 snapshot으로 사용합니다. 빈 응답이나 HTTP 오류가 나면 임의의 대체 summary를 저장하지 않고 요청을 context_compaction_failed로 종료하며, 해당 turn의 answer와 checkpoint update도 진행하지 않습니다.

Streaming 요청에서는 첫 summarization event에 다음 진행 문구를 reasoning 영역으로 한 번만 보냅니다. Summary token stream 자체는 계속 내부 전용이며 non-streaming 응답과 terminal artifact의 구조도 바뀌지 않습니다.

Compaction progress
대화가 길어져 이전 내용을 정리하고 있습니다.

물리 ChatOpenAI 호출 수는 compaction 경로에 따라 다음처럼 해석합니다.

상황정상적인 호출 구성
짧은 요청Answer 1회
한 chunk로 끝나는 compactionSummary 1회 + Answer 1회
provider가 먼저 context overflow를 반환해 복구하는 경우실패한 Answer 1회 + Summary 1회 + 재시도 Answer 1회
여러 chunk 또는 rolling merge가 필요한 경우Summary unit마다 1회 + Answer 1회

한 chunk 정상 compaction은 trace에서 다음처럼 보입니다.

model
├─ compaction (Chain)
│  └─ ChatOpenAI (Generation)
└─ ChatOpenAI (Generation)

compaction은 Summary model invocation이며, 환경에 따라 물리 provider Generation이 그 아래 보입니다. 그 뒤 ChatOpenAI Generation은 압축된 context로 재개한 Main Agent Answer 요청입니다. 기존처럼 compaction과 provider Generation 사이에 추가 ChatOpenAI (Chain)은 생기지 않습니다.

Summary 호출도 현재 Main Agent의 ModelRequest에서 gateway header를 다시 구성합니다. 따라서 User-Id, User-Type, Chat-Id, 새 Prompt-Msg-Id, X-dep-ticket, api-key, Send-System-Name, Accept가 실제 HTTP 요청에 포함됩니다. 필수 request context가 없으면 provider까지 보내지 않고 명시적 compaction 오류로 끝납니다.

원문 대신 FE-visible transcript의 길이와 SHA-256 cursor만 private state에 남깁니다. 같은 chat의 다음 짧은 요청에는 직전 내용이 보존되지 않았다는 private notice를 한 번만 모델에 주입하므로, 사용자가 “아까 내용을 요약해 줘”라고 해도 내용을 안다고 답하지 않습니다. 관련 없는 짧은 질문은 그대로 정상 처리합니다.

System prompt와 Harness Profile​

Main agent의 서비스 정체성, 검색 정책, filesystem 사용 규칙은 계속 configs/system_prompt.jinja2 한 곳에서 관리합니다. Library upgrade로 생긴 Harness Profile은 이 prompt를 대체하는 별도 하드코딩 계층으로 사용하지 않습니다.

현재 Harness Profile의 역할은 model별 native middleware 구성을 공식 extension point로 조정하는 것입니다. Runtime은 main/subagent model에서 profile key를 계산하고, native 기본 summarization middleware를 제외한 뒤 RAG 설정을 반영한 middleware를 graph마다 명시적으로 추가합니다. 이전처럼 library module의 global factory를 잠시 바꾸지 않으므로 여러 graph가 동시에 compile될 때도 설정 경계가 분명합니다.

Prompt and middleware composition
configs/system_prompt.jinja2
        +
model Harness Profile: native summarization 제외
        +
graph middleware: RAG compaction 설정 명시 주입
        =
main/subagent runtime

향후 Profile이 tool description이나 prompt adjustment를 지원하더라도, 현재 정책을 임의로 옮기거나 model 이름별 if 분기를 추가하지 않습니다. 실제로 필요한 model 차이가 생겼을 때 선언형 profile로 합의한 항목만 관리합니다.

LLM gateway / Model catalog​

ENV 또는 파일필수 여부기본값설명
LLM_X_DEP_TICKET필수없음main model gateway 호출에 전달하는 dependency ticket입니다. 비어 있으면 production startup이 실패합니다.

LLM_TIMEOUT보다 먼저 300초 근처에서 끝나는 이유는 무엇인가요?​

Application 밖의 Ingress, API gateway, load balancer read/idle timeout이 먼저 만료할 수 있습니다. LLM_TIMEOUT은 Main/Internal LLM operation의 상한이지 바깥 proxy 정책을 늘리지 않습니다. 300초는 repository의 고정 기본값이 아니므로 배포 cluster의 Ingress annotation, controller ConfigMap, gateway/load balancer 정책을 함께 확인합니다.

Storage​

ENV필수 여부기본값설명
POSTGRES_DSN필수없음PostgreSQL host/database/account 연결 문자열입니다. schema/search path option은 넣지 않습니다. production에서는 비어 있으면 startup이 실패합니다.
SERVICE_NAME필수없음lower snake_case service namespace입니다. service schema와 DBA-managed usage child table 이름을 함께 정합니다.
RUN_CURSOR_SECRET필수없음/v1/runs cursor를 서명하는 서버 전용 HMAC secret입니다. 외부에 노출되면 안 됩니다.
ENCRYPTION_MASTER_KEY필수없음openssl rand -base64 32로 한 번 생성해 Secret에 저장하는 master key입니다. Memory·Summary AES-256-GCM, checkpoint AES-EAX, API Key HMAC-SHA256용 HKDF subkey를 따로 파생하며 누락·형식 오류 시 startup이 실패합니다.
ADMIN_SEND_SYSTEM_NAME필수없음Key/Permission API를 bypass할 trusted sender의 CSV입니다. 각 항목은 exact match하며 _test와 예약값 api, invalid_send_system_name은 허용하지 않습니다.
ALLOWED_SEND_SYSTEM_NAME선택빈 목록API Key와 Permission API를 사용하는 Sub Frontend base name CSV입니다. _test, 예약값, Admin 목록과 겹치는 이름은 허용하지 않습니다.
PERMISSION_API_URL필수없음GET /users/{AD ID}/roles를 호출할 base URL입니다. 내부 timeout은 5초입니다.

SEND_SYSTEM_NAME은 Agent Runtime이 model gateway로 내보내는 outbound 값이고, ADMIN_SEND_SYSTEM_NAME은 Chat 요청의 orch.identity.send_system_name과 비교하는 inbound trusted sender 목록입니다. 두 값은 방향과 용도가 다릅니다.

Trusted sender and Sub Frontend example

두 목록은 공백과 빈 항목을 제거하고 중복을 없애지만, 항목의 대소문자나 내부 문자열은 정규화하지 않습니다. 따라서 KAI_LLM과 kai_llm은 서로 다른 이름입니다. Admin 목록은 suffix를 제거하지 않으므로 KAI_LLM_test를 Admin 값으로 등록할 수 없고 요청에서도 KAI_LLM으로 간주하지 않습니다. _test 제거는 Allowed Sub Frontend 요청에만 적용합니다.

Trusted sender 이름은 credential이 아닙니다

Admin 목록에 들어 있는 sender는 x-api-key와 Permission API를 생략하고 요청 Permission Groups를 그대로 신뢰합니다. 외부 caller가 send_system_name을 임의로 지정할 수 있는 경계에 이 목록을 그대로 노출하면 권한 bypass가 됩니다. API Hub 또는 Ingress는 Admin 목록의 sender를 인증된 내부 caller에게만 부여하거나 검증해야 하며, 일반 개인 API caller가 이 값을 선택할 수 없게 해야 합니다.

Observability / Runs read​

ENV필수 여부기본값설명

LANGFUSE_PUBLIC_KEY선택없음Langfuse public key입니다.
LANGFUSE_SECRET_KEY선택없음Langfuse secret key입니다.
LANGFUSE_RUN_READ_TIMEOUT선택5Runs detail/evidence를 Langfuse에서 읽을 때의 전체 timeout입니다. 0보다 크고 30 이하이어야 합니다.

LangGraph와 Langfuse는 모두 session_id=user_id:chat_id를 사용합니다. Langfuse에는 user_id도 user/metadata로 적재됩니다. 일반 chat turn은 LangGraph, LLM, tool observation과 terminal run.artifact child observation을 같은 trace에 남깁니다. HITL이 발생하면 질문 요청과 하나 이상의 resume 요청이 각각 run_id로 결정되는 trace를 만들고, interaction_id, parent_run_id, phase_index로 관계만 유지합니다. 따라서 Sessions·Tracing 화면에 runtime.run.*가 별도 trace로 추가되지 않습니다. 같은 session 안의 개별 요청은 run_id와 request_id로 구분합니다. Public Runs detail은 별도 allowlist를 쓰므로 Langfuse에 저장된 user_id를 그대로 반환하지 않습니다. 각 trace의 대표 input/output은 현재 user 메시지와 현재 assistant 응답만 담습니다. 이전 대화를 포함한 실제 model context는 trace tree의 ChatOpenAI child에서 확인합니다. run.artifact.output은 terminal run, loop, turn_evaluation을 담습니다. Turn Evaluation은 별도 evaluator observation으로 만들지 않으며, artifact에도 observation 개수 marker를 두지 않습니다.

어떤 실행 결과가 evidence에 남나요?​

mcp_server.json에 tool 목록을 따로 선택하지 않습니다. Langfuse에 observation으로 기록된 main/subagent, model 호출, MCP/tool, Skill, guardrail, HITL, error가 evidence에 남습니다.

Tool result는 해당 observation의 output에 JSON-safe 형태로 보존됩니다. Tool이 timeout이나 exception으로 실패해도 observation을 버리지 않고 해당 항목에 error.message를 반환합니다. 다만 Langfuse에 기록되지 않은 provider-private reasoning은 Runs API가 복원할 수 없습니다.

Turn Evaluation은 LangGraph 실행 node가 아니므로 evidence observation에 섞지 않습니다. 실제 validated response 배열은 Langfuse UI의 terminal run.artifact.output.turn_evaluation에서 호출 순서대로 확인합니다. run.artifact에는 run, loop, turn_evaluation이 있으며, 별도의 observation 개수 marker는 저장하지 않습니다.

Langfuse 원본과 Evidence의 차이​

Langfuse trace는 UI와 기존 분석을 위해 raw 입출력을 보존합니다. Evidence는 실행 의미를 보존하되, 다음 고정 내부 설정만 공개 projection에서 구조적으로 제외합니다.

항목Evidence 결과
Main Agent 소유 model 호출의 system / developer message제외합니다. configs/system_prompt.jinja2를 문자열로 찾아 지우는 것이 아니라 Main model 호출의 내부 지침 message 전체를 제외합니다.
Subagent 소유 model 호출의 system prompt보존합니다. 어떤 위임과 제약으로 동작했는지 분석하는 데 필요한 정보입니다.
Model input의 Tool description / JSON Schemarole="tool"이고 content.type="function"인 구조적 정의 message만 제외합니다. 실제 Tool result message는 유지합니다.
후속 Model의 누적 input snapshot직전 input의 정확한 연장이고 추가분이 이미 보이는 Model·Tool·Skill·Agent observation으로 모두 설명되면 생략합니다. Agent의 첫 Model input과 새 user/system 맥락·compaction 경계는 보존합니다.
Tool input의 최상위 runtime제외하고 실제 Tool argument는 유지합니다.
Framework/SDK metadata와 내부 ID제외합니다. 소유 관계는 중첩 구조 자체로 표현합니다.

이 필터는 문자의 일부를 가리거나 길이로 자르는 방식이 아닙니다. Main/subagent 구분은 trace의 native ancestry, Tool 정의 구분은 message의 role/type 구조를 사용합니다.

Public Evidence의 type="model"은 LLM 호출 한 번을 뜻하고 name은 provider model ID가 아니라 그 호출을 소유한 Agent 이름입니다. Langfuse UI의 raw observation은 기존 Generation으로 보입니다. 후속 model node에 input이 없어도 실행 누락이 아니라, 앞선 timeline에 이미 나온 내용만 누적된 snapshot임을 뜻할 수 있습니다. 해당 호출의 정확한 전체 input은 Langfuse raw Generation에서 확인합니다.

관측 가능성과 민감정보 보호는 targeted policy로 분리합니다. 일반 workspace 분석 내용은 Langfuse에서 진단할 수 있게 유지하되 credential key, Authorization/Bearer, JWT, 주민·외국인등록번호는 SDK input/output masking과 최종 OpenTelemetry span export에서 모두 가립니다. 이름·이메일·전화번호까지 임의로 넓게 가리는 정책은 적용하지 않습니다. 운영 검증은 root뿐 아니라 middleware/model/tool child observation 전체를 대상으로 해야 합니다. Local E2E Compose를 사용할 때는 host API의 Langfuse key가 Compose 초기화 project와 같아야 합니다. /project/local-project에서 trace가 0개이고 API log에 OTLP 401이 보이면 LANGFUSE_PUBLIC_KEY=pk-lf-local-e2e, LANGFUSE_SECRET_KEY=sk-lf-local-e2e로 맞춘 뒤 host API를 재시작합니다.

LLM request correlation​

Caller가 보낸 orch.x_request_id는 API 경계에서 request_id로 이름만 정규화되어 한 RAG 질문·응답 pair의 dedup, usage log, run/Langfuse correlation에 사용됩니다. 하나의 pair 안에서도 Main Agent, subagent, Turn Evaluation, Deep Search, compaction이 provider를 여러 번 호출할 수 있으므로, LLM gateway header는 다른 수명을 가집니다.

식별자수명사용처
request_id한 inbound RAG API 요청dedup, PostgreSQL, run, log, Langfuse metadata
Chat-Id같은 chat_id를 쓰는 대화Main/subagent/Internal LLM/compaction gateway header
Prompt-Msg-Idprovider의 물리 LLM HTTP 호출 1회모든 LLM 호출 직전에 새 UUID 생성

Schema repair와 같이 Internal LLM을 두 번 호출하면 두 호출의 Chat-Id는 같지만 Prompt-Msg-Id는 다릅니다. Caller의 x_request_id를 outbound Prompt-Msg-Id로 복사하지 않습니다. Direct MCP 호출처럼 chat context가 없는 Internal LLM은 Chat-Id를 생략할 수 있지만, Prompt-Msg-Id는 그래도 호출마다 새로 만듭니다.

x_request_id와 LLM Prompt-Msg-Id가 다른 이유는 무엇인가요?​

x_request_id는 caller가 만든 RAG API 요청·dedup ID이고, 서버에서는 request_id로 정규화합니다. 한 요청 안에서 Main Agent, Tool 후 Main Agent, Turn Evaluation, Deep Search, compaction 등이 LLM을 여러 번 호출할 수 있습니다. Gateway에서 이 물리 호출을 구분하려고 Prompt-Msg-Id를 호출마다 새 UUID로 만듭니다. 같은 대화의 LLM 호출은 Chat-Id로 묶습니다.

HTTP 200이면 Streaming 요청이 성공한 건가요?​

7. Manifest, Probe, Search​

Manifest, Probe, Search는 usage table에 행을 만들지 않습니다. Search의 X-Request-Id와 Probe의 metadata.x_request_id는 response correlation에 계속 사용할 수 있지만, 이 ID로 Chat usage table을 조회할 수는 없습니다. 이 API family의 오류와 dependency latency는 application log와 trace에서 확인합니다.

Probe가 usage accepted row를 사용하지 않으므로 같은 payload를 재시도하면 이전의 409 duplicate 응답 대신 두 호출 모두 RAG workload를 실행합니다. 별도 idempotency store는 현재 계약에 포함하지 않습니다.

Runtime이 제공하는 native tool은 ls, read_file, write_file, edit_file, glob, grep과 subagent용 task입니다. write_file과 edit_file은 /workspace/**에서만 허용하며 shell이나 execute는 제공하지 않습니다. Filesystem permission은 model의 tool 호출을 막고, backend는 path traversal과 read-only 경계를 다시 강제합니다.

Quota는 UTF-8 byte 크기로 계산합니다. 한 파일이 512 KiB를 넘거나 thread 전체가 2 MiB를 넘으면 write/edit은 workspace_quota_exceeded로 실패하며 기존 파일을 조용히 덮어쓰지 않습니다. 두 설정은 양의 정수여야 하고 file limit이 total limit보다 크면 startup이 실패합니다.

Workspace는 사용자 download 공간이 아닙니다. System prompt는 Agent에게 파일을 쓴 뒤 실제 결과를 최종 채팅 본문에 포함하도록 지시합니다. 여기에 더해 runtime은 현재 pass에서 성공한 /workspace write/edit이 있었고 답변이 비었거나 path/save-only인 경우에만 보수적으로 한 번 더 이어 쓰게 합니다. 단순히 답변에 /workspace 문자열이 있다는 이유로 continuation하지 않습니다.

ORG_PROCESS는 이 Developer Guide의 MCP, Skill, Agent 설정 형식을 보여 주기 위한 예시입니다. 고정 필수 권한 그룹이 아니며 실제 운영에서는 서비스의 권한 정책에 맞는 그룹명을 사용합니다.

관리 기준:

설정기준
enabledserver를 runtime에서 완전히 켤지 정합니다. 임시 비활성화는 false, 기본값은 true입니다.
includeInManifestRouter가 볼 capability면 true, 내부 전용이면 false

timeout이 MCP server의 tool call을 기다리는 시간입니다. 미지정 시 내부 기본 60초이며, 기본 asset도 각 MCP에 60초를 명시합니다. stdio MCP는 host wrapper가 적용하고, HTTP/streamable MCP는 adapter connection timeout으로도 전달됩니다.
sse_read_timeoutstreamable/SSE MCP 연결이 열린 뒤 다음 이벤트를 기다리는 시간입니다. 미지정 시 adapter 기본 300초를 사용하므로, 특별히 더 긴/짧은 event read 상한이 필요한 서버에만 둡니다.
access.permission_groups권한 제어가 필요해 특정 사용자 그룹에만 server를 노출할 때 사용

enabled=false는 entry를 문서상 보존하면서 해당 MCP server를 완전히 끄는 배포 옵션입니다. 이 경우 runtime tool load, request-scoped injection, manifest discovery, semantic tracing에서 모두 제외됩니다. 실행은 유지하되 Router manifest에서만 숨기려면 includeInManifest=false를 사용합니다.

MCP tool은 별도 선택 목록 없이 Langfuse observation으로 기록됩니다. Runs evidence에서 해당 tool observation의 JSON-safe input/output을 보고, 이 항목을 감싼 agent의 observations 배열로 실행 내용과 소유 agent를 함께 확인할 수 있습니다. 이때 최상위 input.runtime은 framework 실행 객체이므로 public Evidence에서 제외되지만, 실제 Tool argument와 result는 유지됩니다.

access.permission_groups는 MCP server visibility를 정하는 app-owned metadata입니다. access가 없거나 빈 배열이면 public MCP이고, 값이 있으면 chat request의 orch.rag_params.permission_groups와 하나라도 겹치는 요청에서만 main agent가 해당 MCP tool을 볼 수 있습니다. 이 metadata는 MCP process나 HTTP endpoint로 전달되지 않으며, 실제 운영 권한 그룹명에 맞춰 작성해야 합니다.

requestScopedInjection은 별도 목적입니다. 이미 노출이 허용된 tool을 호출할 때 MCP server가 필요로 하는 값을 옮깁니다. destination은 body 또는 header로 명시하며, from은 chat body의 정규화 field와 inbound HTTP header를 함께 검색합니다. 따라서 body와 header 사이의 네 가지 방향을 모두 표현할 수 있습니다. header destination은 HTTP/SSE 계열 MCP에서만 허용됩니다. header[].to에는 X-User-Id처럼 downstream에 실제로 보낼 HTTP header 이름을 적습니다. Source field의 snake_case를 그대로 복사하는 자리가 아니므로 단어는 하이픈으로 구분해야 합니다. snake_case는 source field와 body destination에 사용합니다. HTTP header 이름은 대소문자를 구분하지 않아 X-User-Id, x-user-id, X-USER-ID를 같은 이름으로 비교하며, 문서와 설정에서는 읽기 쉬운 X-User-Id 표기를 일관되게 사용합니다.

requestScopedInjection은 권한을 여는 설정인가요?​

아닙니다. requestScopedInjection은 이미 허용된 MCP tool을 실행할 때 request body/header 값을 tool argument나 HTTP MCP header에 넣는 설정입니다. body와 header destination을 명시하며, HTTP header destination은 HTTP/SSE 계열 MCP에서만 쓸 수 있습니다. 예를 들어 RAG tool argument에 permission_groups를 넣거나 inbound correlation header를 downstream MCP header로 전달할 수 있습니다.

이 설정만 있다고 해서 권한 없는 MCP가 보이거나 실행되지는 않습니다.

timeout은 transport별 적용 위치가 다릅니다. stdio MCP에서는 SDK connection 인자로 넘기지 않고 RAG API가 tool 실행을 감싸는 상한으로 사용합니다. HTTP/streamable MCP에서는 adapter connection timeout으로도 전달하고, 같은 값으로 tool 실행도 감쌉니다. 이와 별도로 RAG API는 MCP_DISCOVERY_TIMEOUT으로 server별 discovery 전체를 감싸므로, 느리거나 응답하지 않는 MCP 하나가 manifest를 오래 막지 않습니다. Manifest는 실패한 server만 빠진 partial inventory를 반환할 수 있지만, Chat은 요청에 visible한 enabled MCP 하나라도 discovery가 실패하면 partial tool set을 쓰지 않고 503 mcp_discovery_failed로 닫습니다.

Manifest에 MCP tool이 빠져 있거나, 보이는데 Chat이 503인 이유는 무엇인가요?​

Manifest는 server별 best-effort static inventory입니다. enabled=false, includeInManifest=false, discovery timeout/오류인 MCP는 빠질 수 있고 다른 server inventory는 계속 반환됩니다. Chat은 현재 사용자에게 visible한 enabled MCP 세트를 전부 로드해야 하므로 하나라도 discovery가 실패하면 partial tool set으로 실행하지 않고 503 mcp_discovery_failed로 닫습니다.

Manifest에는 요청별 permission_groups가 없으므로 restricted Skill/Agent 설명도 보일 수 있습니다. 실제 Chat tool/Skill/Agent 노출은 요청 권한으로 다시 필터링합니다.

stdio MCP의 command가 python 또는 python3이면 RAG API process가 실행 중인 Python executable로 정규화됩니다. Local E2E처럼 host API를 .venv에서 띄우면 child MCP도 같은 .venv dependency를 사용합니다. 절대 경로나 별도 launcher처럼 명시적인 custom command는 그대로 전달되므로, 그 interpreter에는 필요한 MCP dependency가 설치되어 있어야 합니다.

sse_read_timeout은 tool 실행 전체 시간을 뜻하지 않습니다. streamable/SSE MCP 연결이 이미 열린 뒤 "다음 event가 오지 않는 침묵 시간"을 얼마나 기다릴지 정하는 값입니다. 기본 asset은 adapter 기본 300초를 사용하므로 이 field를 명시하지 않습니다.

노트

GET /v1/manifest는 요청별 permission body가 없는 정적 inventory입니다. Router에 보일지 여부는 includeInManifest와 discovery 성공 여부로 결정하고, 사용자별 MCP visibility는 chat runtime에서 access.permission_groups로 결정합니다.

Skill​

Skill은 directory 이름과 frontmatter name이 같아야 합니다.

팁

Skill description은 /v1/manifest에도 노출됩니다. Router나 운영자가 읽어도 이해할 수 있도록 짧은 목적 문장으로 쓰고, 자세한 작업 절차는 본문에 작성합니다.

SKILL.md
---
name: evidence-review
description: Review answer grounding against retrieved RAG evidence.
access:
  permission_groups:
    - ORG_PROCESS
---

Check whether the answer separates evidence-backed facts from inference.

Agent​

Agent는 assets/agents/<name>.md 하나로 선언합니다.

정보

Agent는 부모 대화 전체를 자동으로 알지 못합니다. main agent가 넘긴 task description과 허용된 tool/skill만 보고 좁은 검토를 수행하도록 설계합니다.

Agent definition
---
name: process-reviewer
description: Review process-engineering answers for missing assumptions and caveats.
skills:
  - evidence-review
tools:
  - mcp__retriever__rag_search
access:
  permission_groups:
    - ORG_PROCESS
---

Review the draft answer for process consistency and missing caveats.
Return concise private guidance to the main agent.
