API Key Management

Sub Frontend와 개인 API가 Chat에 사용할 binding API Key를 발급·조회·만료 갱신·폐기하는 내부 운영 API입니다.

위험

이 endpoint에는 별도 application credential이 없습니다. 배포 시 Ingress·network policy에서 /internal/*를 인증된 운영자에게만 노출해야 합니다.

Binding 규칙​

용도binding_fieldbinding_valueChat 검증 대상
개인 APIuser_idemployee.one 같은 AD IDorch.identity.user_id
Sub Frontendsend_system_namemedic 같은 whitelist base name마지막 _test를 제거한 sender

Key는 artk_<UUID>.<random-secret> 형식입니다. 원문은 발급 응답에서 한 번만 보여 주고, PostgreSQL에는 HKDF로 분리한 HMAC-SHA256 key로 계산한 hash만 저장합니다.

시간 입력과 표시​

expires_at은 Runs와 같은 유연한 시간 형식을 받습니다. Timezone이 없는 값은 KST로 해석하고, 모든 응답의 issued_at, expires_at, revoked_at은 +09:00 KST로 표시합니다.

입력 예해석
2027-02-202027-02-20 00:00:00 KST
2027-02-20 18:302027-02-20 18:30:00 KST
2027-02-20T18:30:452027-02-20 18:30:45 KST
2027-02-20T09:30:00Z같은 순간인 2027-02-20 18:30:00 KST
2027-02-20T18:30:00+09:002027-02-20 18:30:00 KST

PostgreSQL TIMESTAMPTZ는 timezone 이름이 아니라 같은 순간을 저장합니다. Adminer 같은 DB client가 UTC 등 다른 session timezone을 사용하면 화면의 offset은 달라질 수 있지만 API가 반환하는 KST 시각과 가리키는 순간은 같습니다.

POST /internal/v1/api-keys​

Sub Frontend Key 발급
{
  "binding_field": "send_system_name",
  "binding_value": "medic",
  "expires_at": "2027-02-20 18:30"
}

성공하면 201 Created와 원문 api_key를 반환합니다. expires_at은 발급 시각보다 나중이어야 합니다. Sub Frontend binding에 _test를 넣지 않습니다.

Created response
{
  "key_id": "7c68ab63-184b-48cd-82eb-a28692d94504",
  "api_key": "artk_7c68ab63-184b-48cd-82eb-a28692d94504.<secret>",
  "binding_field": "send_system_name",
  "binding_value": "medic",
  "issued_at": "2026-08-20T16:00:00+09:00",
  "expires_at": "2027-02-20T18:30:00+09:00"
}

PATCH /internal/v1/api-keys/{key_id}​

만료 시각만 변경합니다.

{
  "expires_at": "2027-08-20"
}

날짜만 보내면 해당 KST 날짜의 00:00으로 갱신됩니다. Offset이나 Z를 보내도 응답은 같은 순간의 KST 표기로 정규화됩니다.

GET /internal/v1/api-keys​

key_id, binding_field, binding_value를 선택적 query filter로 사용할 수 있습니다. 응답은 metadata와 active, expired, revoked status만 포함하고 Key 원문과 hash는 포함하지 않습니다. 모든 timestamp는 KST +09:00으로 표시됩니다.

DELETE /internal/v1/api-keys/{key_id}​

row를 물리 삭제하지 않고 revoked_at을 기록한 뒤 204 No Content를 반환합니다. API Key 검증 결과는 cache하지 않으므로 폐기는 다음 Chat 요청부터 반영됩니다.

API Key 상태는 api_keys에만 보관합니다. 발급·갱신·폐기 작업 이력을 위한 별도 감사 table은 만들지 않습니다.
