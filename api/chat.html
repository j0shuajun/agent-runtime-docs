Chat

OpenAI-compatible chat payload에 RAG 전용 orch metadata를 추가해 agent 실행을 시작합니다. 일반적인 사용자 화면에서는 POST /v1/chat/completions만 호출하면 됩니다.

경고

같은 user_id:chat_id에서 이전 stream이 끝나기 전에 다음 chat 요청을 보내면 409 session conflict가 발생할 수 있습니다. 화면에서는 이전 stream이 끝났거나 사용자가 stop한 뒤에 다음 질문을 보내야 합니다.

POST /v1/chat/completions​

Request
curl -N "$AGENT_RUNTIME_API_BASE/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model-id-from-catalog>",
    "stream": true,
    "messages": [
      {"role": "user", "content": "deployment delay 발생 원인을 설명해줘"}
    ],
    "orch": {
      "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
      "x_request_id": "896cd7ad-8e3c-4c85-b918-a294d133c44e",
      "identity": {
        "user_id": "user-1",
        "send_system_name": "<메모결재 양식에 기입한 시스템명>"
      },
      "rag_params": {
        "index": "rag-index",
        "permission_groups": ["example-team"]
      }
    }
  }'

요청 값​

필드필수입력 기준비고
model예Catalog에서 받은 값을 지정합니다.서버가 실제 model gateway를 선택할 때 사용합니다.
messages예최소 1개 이상의 message를 보냅니다.문자열 또는 text/image multimodal part를 받습니다. system은 한 개까지 검증을 통과하지만 agent context에서는 제외됩니다.
orch.identity.user_id운영상 필수로그인 사용자나 업무 시스템의 안정적인 사용자 id를 전달합니다.세션 격리, 중복 요청 방지, 운영 로그의 기준입니다. Placeholder는 400으로 거절됩니다.
orch.identity.send_system_name운영상 필수메모결재 양식에 기입한 시스템명을 전달합니다.시스템 연계를 위해 대량 호출하는 경우에만 test를 사용합니다.
orch.chat_id운영상 필수새 대화마다 UUID를 만들고 같은 대화에서는 유지합니다.대화 이력과 HITL 재개의 기준입니다. Nil UUID는 400입니다.
orch.x_request_id운영상 필수새 사용자 요청마다 UUID를 만듭니다.같은 값의 재시도는 이전 응답 재생 없이 409 duplicate_request로 중복 실행을 막습니다.
orch.rag_params.index아니오Catalog의 index를 comma-separated string으로 지정합니다.비어 있으면 설정된 전체 RAG index, nonblank이면 allowlist와 교집인 항목만 사용합니다.
orch.rag_params.permission_groups아니오사용자의 실제 접근 권한 그룹을 전달합니다.빈 목록도 받지만 RAG 문서와 restricted MCP, Skill, Agent 노출이 줄어들 수 있습니다.

max_tokens, max_completion_tokens, temperature, top_p, frequency_penalty, seed, stop 같은 generation control과 generation_config는 호환성을 위해 요청에 포함되어도 오류를 내지 않지만 서버가 validation 전에 폐기합니다. Main Agent와 Internal LLM 설정에는 반영되지 않습니다. stream만 caller가 선택하는 response transport 설정으로 유지됩니다.

orch.identity.send_system_name에는 메모결재 양식에 기입한 시스템명을 사용합니다. 시스템 연계를 위해 대량으로 호출할 때만 test를 사용합니다. 이 값과 optional orch.routing_check는 routing이나 model 선택을 바꾸지 않습니다. 두 값은 usage 원장의 upstream_name을 결정하고, 활성 routing_check는 추가로 streaming routing marker를 한 번 보입니다.

senderrouter 값저장되는 upstream_name
생략, null, 공백무관api
ds_assistanttrue, on, 그 밖의 활성 문자열ds_assistant
ds_assistant생략, null, false, "", "0", "no", "off", "false"현재 SERVICE_NAME
그 밖의 nonblank 값무관입력값 그대로

orch.routing_check가 true, on, 1 등의 활성값이면 streaming 응답에서 assistant role 다음 reasoning_content로 운영자가 설정한 routing 안내를 한 번 보냅니다. 이 표시는 어떤 model을 선택할지 바꾸지 않고, non-streaming 응답에도 추가되지 않습니다.

Usage 원장은 Chat 요청만 저장합니다. Manifest, Probe, Search는 이 table에 행을 만들지 않으므로 endpoint와 operation column도 사용하지 않습니다.

orch를 생략하거나 orch.identity.user_id가 비어 있거나 literal "user_id"인 경우, 또는 chat_id/x_request_id가 nil UUID이면 400 invalid_identity로 거절됩니다. UUID 형식 자체가 잘못되었으면 request schema 검증에서 422 validation_error가 발생합니다.

Streaming 응답​

Streaming response excerpts
data: {"choices":[{"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"choices":[{"delta":{"reasoning_content":"검색 중...\n"},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":"deployment delay은 ..."},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":""},"finish_reason":"stop"}],"orch":{"result_message":{"content":"최종 답변"}},"loop":{"tool_calls":1,"model_calls":1,"stop_reason":"completed","duration_ms":800,"repeats_blocked":0,"compaction":{"occurred":false,"count":0,"cutoff_index":null}}}

data: [DONE]

가독성을 위해 위 예시에서는 각 chunk의 id, object, created, model, choice index와 terminal orch.rag 호환 구조를 생략했습니다. 실제 응답은 이 common envelope field를 포함합니다.

Runtime이 main agent의 첫 progress, content 또는 terminal event를 내기 직전에 {"role":"assistant"} delta가 독립 chunk로 한 번 나옵니다. Routing이 활성화된 요청은 바로 다음 role 없는 reasoning_content delta에 routing 안내를 보냅니다. 이후 progress, content, terminal chunk에서 role을 다시 추가하지 않으므로 [DONE]까지 assistant role은 정확히 한 번만 나와야 합니다.

응답 생성 중 LLM, MCP, graph state 조회, storage, 외부 dependency가 오래 걸리면 agent event가 잠시 없을 수 있습니다. Stream wrapper는 이런 idle 구간에도 OpenAI-compatible reasoning_content chunk로 생각 중... heartbeat를 보냅니다. FE가 60초 동안 content 또는 reasoning_content를 받지 못하면 오류를 표시하는 환경에서도 이 heartbeat는 사용자-visible 진행 신호로 동작합니다.

Idle heartbeat
data: {"choices":[{"delta":{"reasoning_content":"생각 중...\n"},"finish_reason":null}]}

이 heartbeat는 답변 본문이 아니므로 content 누적 결과와 섞지 않습니다. 기존 SSE comment keep-alive는 transport 보조 신호일 수 있지만, FE 진행 표시와 idle error 방지는 reasoning_content heartbeat를 기준으로 처리합니다.

노트

Runtime 준비가 heartbeat interval보다 길면 생각 중... delta가 assistant role보다 먼저 올 수 있습니다. Heartbeat는 대기 연장 신호이고, assistant role이 실제 main-agent 출력 시작 신호입니다. FE는 첫 chunk가 항상 role일 것으로 가정하지 말고 각 delta field를 독립적으로 처리해야 합니다.

응답 위치처리 방식
choices[0].delta.roleassistant는 stream 시작 신호입니다. Assistant message container를 준비하되 본문으로 누적하지 않습니다.
choices[0].delta.content사용자에게 보여줄 답변으로 누적합니다.
choices[0].delta.reasoning_contentRouting 안내, heartbeat, 검색, tool, agent 진행 상태로 표시할 수 있습니다. 답변 본문과 섞지 않습니다.
choices[0].finish_reasonstop, hitl, error 같은 종료 상태를 확인합니다.
orch.result_message.content마지막 chunk에 포함된 최종 답변입니다. 중간 delta를 이미 누적했다면 중복 표시하지 않습니다.
usageStreaming과 non-streaming Public Chat 응답에는 포함되지 않습니다. Token 사용량은 내부 관측과 usage ledger에서 관리합니다.
loop.compaction긴 대화에서 role-aware rolling compaction이 이번 요청 중 관측됐는지 보여주는 metadata입니다. Snapshot text나 raw path는 포함하지 않습니다.
hitl추가 질문이 필요한 경우 마지막 chunk에 포함됩니다. 자세한 처리 방식은 아래 HITL(Human-In-The-Loop) 섹션을 참고합니다.
erroragent 실행이 오류로 끝난 경우 마지막 chunk에 포함됩니다.

Agent가 내부 filesystem을 사용하면 다른 tool과 같은 progress 형식을 사용합니다.

Filesystem progress
data: {"choices":[{"delta":{"reasoning_content":"[Tool] write_file\n"},"finish_reason":null}]}

data: {"choices":[{"delta":{"reasoning_content":"[Tool] read_file\n"},"finish_reason":null}]}

/skills/<name>/SKILL.md를 읽는 경우에는 기존 [Skill] <name> 표시를 사용합니다. 일반 질문에서 filesystem이 필요하지 않으면 이 progress는 나타나지 않습니다. /workspace 파일은 Agent의 thread-scoped 내부 작업물이며 별도 download 응답이 아닙니다. 따라서 성공 응답은 파일 경로만 알리는 대신 실제 요청 결과를 content에 포함합니다.

Non-streaming 응답​

stream: false이면 OpenAI 일반 non-stream 형식의 JSON body를 한 번에 받습니다. 최종 답변은 choices[0].message.content에서 확인합니다. 추가 질문으로 끝나면 사용자에게 보여줄 질문이 같은 위치에 들어가고 choices[0].finish_reason 값은 hitl입니다. 반면 agent 실행이 실패하면 choices 형식이 아닌 HTTP 500 공통 error envelope를 반환합니다. Streaming에서만 response가 이미 200으로 시작된 후의 실패를 terminal finish_reason: "error"로 표시합니다. Streaming과 마찬가지로 top-level usage는 반환하지 않습니다.

Compaction metadata
{
  "loop": {

      "count": 1,

cutoff_index는 긴 대화 중 snapshot으로 접힌 누적 checkpoint message 경계입니다. Snapshot 본문, summary 길이, raw offload path, raw history content는 Chat 응답에 나오지 않습니다. 다만 streaming 요청에서 compaction summary가 시작되면 reasoning_content로 대화가 길어져 이전 내용을 정리하고 있습니다.를 한 번 보냅니다. 이는 summary 본문이 아니라 서비스가 생성한 진행 안내이며 non-streaming 응답과 terminal artifact에는 추가하지 않습니다.

Turn Evaluation이 정당하게 revision을 시작해 assistant 답변이 두 블록으로 나뉘어도 SSE의 delta.content에는 구분용 chunk를 추가하지 않습니다. Terminal orch.result_message.content에는 두 답변 블록 사이에 빈 줄을 넣어 누적 본문이 붙어 보이지 않게 합니다.

새로 append할 입력 하나만으로 token trigger를 넘으면 streaming terminal은 finish_reason="error", loop.stop_reason="context_input_too_large"와 아래 문구를 반환합니다.

입력 내용이 처리 한도를 초과하여 요청을 실행하지 못했습니다.
해당 입력 내용은 대화 문맥에 저장되지 않았습니다.
내용을 나누어 다시 보내 주세요.

같은 chat에서 다음 짧은 입력은 정상 실행됩니다. 거절된 원문은 active conversation state에 포함되지 않으므로 모델이 그 내용을 복원하거나 알고 있다고 답하지 않습니다. 기존 non-stream 오류 envelope 계약은 유지되며, FE의 기본 streaming 경로에서는 위 terminal payload를 직접 사용합니다. Langfuse raw inbound trace는 기존 관측 계약대로 기록될 수 있습니다.

HITL(Human-In-The-Loop)​

HITL은 API가 답변 대신 사용자에게 추가 질문을 돌려주는 상태입니다. HTTP status가 200이어도 choices[0].finish_reason이 hitl이면 완료가 아니라 답변 대기입니다. 클라이언트는 질문을 사용자에게 보여주고, 사용자의 답변을 같은 대화로 다시 보내야 합니다.

가장 단순한 처리 순서는 다음과 같습니다.

  1. 응답의 finish_reason을 확인합니다.
  2. hitl이면 질문 text를 사용자에게 보여줍니다.
  3. 사용자가 답하면 같은 chat_id, 같은 user_id, 새 x_request_id로 다시 요청합니다.
  4. 다시 보낼 때 사용자의 답변을 messages[].content와 hitl.answer에 넣습니다.
확인할 값의미클라이언트 처리
choices[0].finish_reasonhitl이면 사용자 답변이 필요합니다.이 대화를 완료 처리하지 않습니다.
choices[0].message.contentnon-streaming에서 보여줄 질문입니다.그대로 사용자에게 표시합니다.
choices[0].delta.contentstreaming에서 누적되는 질문 text입니다.누적해서 사용자에게 표시합니다.
hitl.question현재 질문의 구조화 정보입니다.필요하면 form label이나 상태 저장에 사용합니다.
hitl.current_index / hitl.total여러 질문 중 현재 위치입니다.예: 2 / 3 표시가 필요할 때 사용합니다.
hitl.id응답에 포함되는 질문 식별자입니다.resume 요청에 다시 보낼 필요는 없습니다.

Streaming HITL 응답​

streaming에서는 질문이 일반 delta.content처럼 먼저 도착할 수 있습니다. 마지막 terminal chunk에서 finish_reason: "hitl"과 hitl을 확인합니다.

HITL streaming response
data: {"choices":[{"delta":{"content":"어느 문서를 기준으로 확인할까요?"},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":""},"finish_reason":"hitl"}],"hitl":{"kind":"ask_user","id":"intr-123","question":{"question":"어느 문서를 기준으로 확인할까요?"},"questions":[{"question":"어느 문서를 기준으로 확인할까요?"}],"current_index":0,"total":1,"reask_count":0,"required":true},"loop":{"stop_reason":"hitl"}}

data: [DONE]

이 예시에서 화면에는 누적한 어느 문서를 기준으로 확인할까요?를 보여줍니다. 마지막 chunk의 delta.content가 빈 문자열이어도 finish_reason이 hitl이면 사용자 답변을 받아야 합니다. data: [DONE]은 stream 종료 표시일 뿐, 최종 답변 완료를 뜻하지 않습니다.

이 예시에서는 choices[0].message.content를 사용자에게 보여주고, 같은 chat_id를 답변 대기 상태로 유지합니다. hitl은 현재 질문과 질문 순서를 구조화해서 담습니다.

답변을 보내서 재개하기​

사용자가 답하면 일반 새 대화를 만들지 말고 기존 대화를 이어갑니다. chat_id와 user_id는 HITL 응답을 받은 요청과 같아야 하고, x_request_id는 새 값이어야 합니다.

Resume request
curl -N "$AGENT_RUNTIME_API_BASE/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model-id-from-catalog>",
    "stream": true,
    "messages": [
      {"role": "user", "content": "SOP-123 문서를 기준으로 확인해줘"}
    ],
    "hitl": {
      "answer": "SOP-123 문서를 기준으로 확인해줘"
    },
    "orch": {
      "chat_id": "2b0e1c88-540d-4af7-85d8-b1e7f6fa865e",
      "x_request_id": "fa9e0675-881d-4437-9d6b-a1d6e9c794ee",
      "identity": {
        "user_id": "user-1",
        "send_system_name": "<메모결재 양식에 기입한 시스템명>"
      },
      "rag_params": {
        "index": "rag-index",
        "permission_groups": ["example-team"]
      }
    }
  }'
값기준
orch.chat_id이전 HITL 응답을 받은 대화의 chat_id를 그대로 사용합니다.
orch.identity.user_id이전 요청과 같은 사용자 id를 사용합니다.
orch.x_request_id새 요청 id를 보냅니다. 이전 값을 재사용하지 않습니다.
messages[].content사용자가 입력한 답변을 대화 이력으로 보냅니다.
hitl.answer사용자의 답변을 resume 값으로 보냅니다. 보통 messages[].content와 같은 문자열입니다.
stream재개 요청도 true 또는 false를 선택할 수 있습니다.

messages[].content와 hitl.answer는 같은 답변으로 맞추는 것이 가장 단순합니다. 값이 다르면 HITL 재개에는 hitl.answer가 사용됩니다. hitl.answer가 없으면 hitl.answers[]의 첫 값, 그것도 없으면 가장 최근 user message를 resume 값으로 사용합니다. 명시적이고 오해가 적은 hitl.answer를 권장합니다.

재개 후 답변이 완성되면 일반 응답처럼 finish_reason: "stop"으로 끝납니다.

Resume streaming response
data: {"choices":[{"delta":{"content":"SOP-123 기준으로 보면 ..."},"finish_reason":null}]}

data: {"choices":[{"delta":{"content":""},"finish_reason":"stop"}],"orch":{"result_message":{"content":"SOP-123 기준으로 보면 ..."}},"loop":{"stop_reason":"completed"}}

data: [DONE]

여러 질문이 이어지는 경우​

답변을 보낸 뒤에도 finish_reason: "hitl"이 다시 올 수 있습니다. 이 경우 추가 질문이 필요한 상태이므로 같은 방식으로 다시 사용자 답변을 받아 resume 요청을 보냅니다.

각 resume 요청은 새 run_id를 갖지만 Runs API에서는 최초 질문 요청의 run을 interaction_id로 공유합니다. parent_run_id는 직전 요청, phase_index는 0부터 시작하는 질문/답변 단계입니다. 클라이언트가 이 값을 만들어 보낼 필요는 없습니다. Langfuse에서는 각 request가 별도 LangGraph trace로 보이고, Sessions에는 각 trace의 현재 user/assistant 질답이 중복 없이 순서대로 보입니다. 모델이 받은 이전 대화 전체는 각 trace의 ChatOpenAI child observation에서 확인합니다.
